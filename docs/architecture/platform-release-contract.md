# Platform, evidence and release contract

Status: **selected V1 design; unimplemented and unqualified**. This contract addresses the [independent review](../reviews/2026-10-13-independent-architecture-review.md), especially platform S1–S6 and architecture findings 7/9/10/12/13, plus the subsequent [brief cross-reference](../reviews/2026-10-13-post-patch-brief-review.md). It supplements the [system architecture](../superpowers/specs/2026-10-13-volnlabs-system-architecture.md). Names and CLI examples are proposed interfaces. Target versions, hardware and numerical physical limits remain required release inputs; missing inputs fail preflight.

## 1. Executable artifacts and identity

V1 supports an **untrusted OCI agent on the server proposing calls to reviewed fixed native skills on the robot**. Generated robot-local code, runtime skill loading and user-provided kernel programs are unsupported V1 execution classes.

Two immutable objects are distinct:

- Agent artifact: OCI digest, entrypoint, configuration/schema digest, approved broker tools and sandbox profile.
- Skill configuration: release-built skill ID, configuration digest, endpoint-contract revision and permitted typed parameters. Its code ships with `actryn-robotd`; installation grants no motion authority.

The restricted launcher originates tenant/job/attempt IDs and binds them to artifact, sandbox, cgroup lifetime, host boot and process lifetimes. `attempt prepare` reserves this identity and a stopped verified sandbox before grant issuance; `attempt start` rechecks the binding before executing the agent. Fork/exec stays within that attempt. Agents cannot override this association through request fields. `actryn-serverd` binds its per-attempt broker channel to that record and authenticates to the robot with a scoped workload credential. The robot independently authorizes that principal, creates a fresh local skill instance, and binds it to an operator-issued grant for the prepared attempt. The operator may prepare several instances within the finite reservation policy below; every instance has one immutable skill/configuration identity and fresh mutable state owned by `actryn-robotd`. The ordinary agent API cannot prepare/activate instances or issue grants.

Fixed skill routines run as bounded native tasks inside `actryn-robotd`; they neither own the effective grant table nor write raw controller bytes. Kernel admission remains mandatory. A new server process or robot-manager lifetime creates new instances; recovered state is diagnostic history, not a resumed grant. The kernel session owner is the registered initial thread-group leader; its exit revokes task authority even if other threads or duplicated descriptors survive. Exact kernel lifetime implementation belongs to the robot contract.

The restrained wheel profile excludes active stabilization/holding claims. Independently progressing controller expiry/protection survives task loss; its electrical response still requires qualification. Future balancing/holding endpoints need their own independently surviving control contract.

The trusted inference broker originates a context binding attempt, inference request ID, observation IDs/content digests, calibration/clock revisions and skill/configuration. It binds the returned tool proposal to a stable parent request key; the first robot proposal supplies that key/digest, and the robot allocates/durably binds its operation ID before any effect. The broker appends the returned ID without rebinding the original key/context. Key-based retries resolve the same record. Context closes on cancellation, skill finish, expiry, replacement or attempt termination; tool proposals cannot substitute a newer observation ID. Robot admission still checks locally retained observation validity. Direct agent model calls, when later supported, carry `agent_declared` lineage. Broker records are `server_attested`, not proof the model attended to an image or protection against a compromised server. Learned diagnoses remain separate from observed failures.

Preparation reserves explicit per-attempt and global instance counts, state/temporary bytes and preparation CPU/work limits **before construction**. The accounting includes active, staged and retiring instances simultaneously, plus fixed control/closure headroom. Preparation uses bounded inputs and a fixed worker/concurrency cap outside the control worker with a finite deadline; publication consumes the existing reservation after the expected-generation and grant checks. Failed activation leaves a staged reservation with a finite lifetime; abandonment, timeout and failed construction release it only after work and buffers finish. Replacement releases the old reservation only after reconciliation and callback/task teardown. Restarts invalidate instances and grants before reconstructing fresh accounting. Deterministic admission/allocation rejection preserves active A; daemon failure invokes owner loss and independent expiry, not an assurance that A continued. No allocation or persistence occurs under the kernel authority mutex.

Stopped prepared server sandboxes also consume finite per-attempt/global count, memory, image-storage and lifetime reservations. Failed start, abandonment or timeout revokes their credentials and reaps their resources before release. Preparation limits and cleanup are part of the release profile, not implementation defaults.

### Request identity and cancellation before ID return

Authenticated `query` and `cancel` accept either an operation ID or `(attempt namespace, client request key)`; the SDK exposes that stable request handle before sending the first proposal. For admission the robot binds that namespace to the authenticated attempt and current robot epoch; agent fields cannot impersonate it. Read-only lookup returns absent/pending/terminal status and never allocates, resends or admits work. Authorized historical queries remain available after epoch retirement. A namespace cannot reopen after teardown or server/robot lifetime change.

The robot manager uses a short per-key registry lock to order allocation, cancellation and kernel submission. First proposal reserves key-record capacity and an operation ID in a non-dispatchable phase, then commits intent **outside the lock**. Persistence applies monotonic key revisions with a terminal-wins transaction check: a delayed intent commit cannot overwrite a cancellation tombstone. After durability, it reacquires the lock and rechecks the cancellation fence, namespace, digest and live conditions before synchronous kernel admission/submission; that call does not wait for UART completion or storage. Cancellation sets the terminal fence in the same order. Thus it either precedes submission or resolves the allocated operation to the existing urgent kernel close path. The kernel remains the sole effective physical authority.

Cancelling an absent key reserves a terminal tombstone and persists it before reporting `KEY_CANCELLED_DURABLE`. A delayed proposal cannot pass the in-memory fence while persistence is pending. Cancelling an allocated key invokes urgent closure without waiting for its cancellation record to persist; storage stalls must not hold the registry lock. `REQUEST_CANCEL_PENDING`, `KEY_CANCELLED_DURABLE`, kernel `LOCALLY_CLOSED` and endpoint `RECONCILED` are separate facts; durable identity closure alone does not establish downstream closure. Acknowledgment loss is resolved by side-effect-free query, never retry-as-lookup.

Retain tombstones and terminal key bindings while their namespace can create work; changed-digest retries reject. Required finite key/storage budgets include reserved cancellation capacity. Exhaustion closes new proposal admission for that namespace instead of evicting live cancellation identity; existing operation cancellation still uses reserved control capacity. On persistence failure report pending/failed durability, never effective durable cancellation. After any manager crash, the old epoch/namespace cannot submit again; unfinished records remain unknown, and recovery cannot revive a key or authority even if the cancellation commit was lost.

### Robot network gateway

`actryn-gatewayd` is an unprivileged, separately sandboxed network relay. It forwards bounded encrypted streams over a protected local transport to `actryn-robotd`; established end-to-end mTLS terminates in the manager. The manager holds the device key and independently authenticates the original principal, certificate scopes, revocation state and prepared-attempt binding. Gateway-provided identity headers or certificate descriptions are not authorization. Disable TLS early data for state-changing requests. The TLS library and bounded RPC decoder remain trusted manager code; this split does not eliminate their review obligations.

The gateway receives no kernel runtime/admin handles, acquisition rights, operator/device keys, intent-database access or direct controller path. Only the registered manager submits runtime operations; the existing separate administrator/acquisition roles remain scoped. A Unix peer credential identifies the relay process, not the remote caller. The manager binds every request to its authenticated principal, current session/robot epoch, attempt namespace, immutable request digest and applicable deadline. Retries resolve the existing stable key without refreshing authority; closed sessions and retired namespaces cannot create work. Historical query/cancel through a freshly authenticated authorized session remains available.

The manager binds relayed sessions to the supervised gateway process lifetime through a retained OS process handle obtained and checked through the protected local service-control path, not a claimed PID or final socket-reference count. Exact peer/handle association and process-exit detection are required implementation tests. Gateway exit/replacement closes affected contexts and revokes associated grants through the urgent kernel path, even if transport descriptors survive elsewhere. Required authenticated-session liveness loss follows the same closure policy. Detection and closure have finite profile limits; no immediate-death guarantee is made. A replacement gateway uses fresh sessions and cannot restore grants. Ordinary agent/client disconnection may leave an already admitted skill running only under its installed continuation policy and original operation/grant/context ceilings. Transport EOF alone is neither successful cancellation nor proof of gateway process death.

The manager independently caps concurrent handshakes/connections, decoder/message sizes, sessions, queued bytes, in-flight requests and cryptographic work. These finite per-principal/global limits reserve control/closure capacity; bulk observations use separate bounded channels and cannot consume that reserve. Gateway-side rate limits are additional defenses, not the bound on trusted work. An unauthenticated or compromised gateway cannot prolong a grant by sending traffic or health messages.

Forwarding acceptance establishes no cancellation stage. Only manager/kernel/controller acknowledgements establish durable key closure, local closure or reconciliation. A compromised gateway can drop or delay remote requests; remote cancellation availability is therefore not guaranteed. Protected local operator query/cancel/revoke/reconcile/rearm reaches the manager directly without gateway, server or cloud access and retains ordinary credential checks. If the manager or Linux stops progressing, kernel owner/deadline checks and independent controller expiry retain their existing roles.

Required fixtures include forged identity fields, encrypted-record/session replay, delayed valid requests, unauthorized widening, gateway restart with duplicated/retained transport descriptors, connection/decoder flooding, cancellation during saturated observation export, lost cancellation replies and local recovery with gateway/server unavailable. Also verify manager death follows the separate registered-owner rule. No new gateway-specific kernel API or transferable command capability is introduced.

## 2. One server sandbox and launch order

Use containerd through its supported API with a restricted launcher. Select one tested OCI runtime/configuration tuple. The launcher accepts declarative approved profiles, never arbitrary host commands, mounts, hooks or runtime options.

Launch order is contractual:

1. Allocate identity and a dedicated cgroup lifetime; reserve attribution before task creation. Prepare immutable image/rootfs and per-attempt broker socket; close all other inherited descriptors.
2. Configure namespaces, mount/device allowlists, UID/capabilities, seccomp, resource limits and network isolation. Attach required enforcement and attribution; record installed identities and coverage.
3. Create the runtime task without executing image/application code. Trusted runtime setup is separately identified. Reject image-supplied hooks and unapproved runtime extensions.
4. Verify task/cgroup binding, policy presence and required collector readiness, then invoke task start. Any preceding failure destroys the prepared task and revokes credentials.

The runtime's create/start boundary and early-process attribution require source/integration tests on the selected version. A backend that cannot establish this order is unsupported. Descendants cannot migrate cgroups, acquire host capabilities or access the container engine. Cleanup revokes the attempt broker/credential and kills/reaps its complete cgroup before releasing the live sandbox registration. Immutable attempt identity remains available for retained evidence and outstanding broker reservations; sandbox cleanup does not erase external-work accounting.

The initial `server-restricted` profile has no routable network interface. External inference/tools go through the per-attempt Unix broker socket, exposing named approved operations rather than caller-selected URLs. The broker holds provider credentials outside the sandbox and applies destination/request limits. Arbitrary direct egress is unsupported in this profile.

Broker work requires atomic per-attempt **and global** reservations before queueing or dispatch: outstanding jobs, request/response bytes, retained output bytes, execution deadlines and applicable model-token/provider-cost limits. These account for queued, running, cancelling and unresolved external work, not just queue length. Policy limits and request/output caps are finite release inputs; provider-charge bounds require enforceable provider limits, otherwise the method is unsupported for that bounded profile. Stream responses into bounded buffers and reject excess without publishing tool proposals. Delegated consumption and unresolved reservations retain attempt attribution in reports, separately from agent cgroup usage.

Reuse the server's SQLite intent store for external-dispatch reservations, committed before dispatch. Broker cancellation or attempt teardown closes publication contexts immediately and rejects new work, but returns capacity only after work and buffers actually terminate. A client timeout or provider cancellation request is not completion. Uncancellable or uncertain calls keep their outstanding/provider reservation; late replies settle accounting but cannot publish into a closed context. Local execution follows the same rule until its task and buffers terminate.

After broker restart, recover unresolved reservations before enabling admissions; do not resend them or free them because the process disappeared. Reconcile through verified provider outcomes, or a provider-enforced upper bound only where that guarantee is established. Otherwise keep that capacity quarantined, including a possible dispatch whose reply/commit was lost. Operator acknowledgment alone cannot clear an unresolved debit. Ambiguous/corrupt reservation storage blocks new dispatch. Completed results retain only their output-storage reservation until consumed/expired and deleted; unused provider budget is returned only after verified settlement. Settled consumption remains charged to the policy accounting period, rather than making successful calls free. This conservative finite accounting may reduce availability but prevents restart/cancel loops bypassing the admission budget.

| Rule | Enforcement / installation check | Evidence and exact limit |
|---|---|---|
| Host files, credentials and management sockets unavailable | Mount allowlist, separate identity, dropped capabilities, no inherited handles; inspect prepared mounts/FDs and negative fixture | Attributed syscall failure plus installed-policy snapshot. `ENOENT`/`EACCES` alone is not a policy-attributed denial. |
| Only minimal approved character devices | Device allowlist plus restricted `/dev`; inspect policy and try a deliberately mounted forbidden dummy device in the test profile | Kernel-observed failed open and policy inventory. Stock device policy supplies no assumed per-denial audit event. |
| No direct external/controller network | Isolated network namespace, no external route or inherited network socket; inspect topology and negative connect test | Failed connect, topology and broker records; do not infer which policy caused an arbitrary network error. |
| Privileged kernel/process operations unavailable | Dropped capabilities and architecture-specific seccomp rules for `bpf`, `perf_event_open`, mount and namespace-changing operations | Fixed reviewed BPF observer records entry/return for selected syscalls; distinguish filter configuration from an enforcement-origin denial event. |
| Bounded CPU/memory/PIDs/I/O | Required explicit cgroup limits; read back effective values | Trusted counters, pressure and process events. Correlation does not establish that one request caused all host pressure. |
| Only allowed broker methods/resources | Broker binds authenticated channel to prepared attempt and checks its fixed method/resource policy before any effect | Broker-origin `policy_denied` with rule/request/attempt identity is an attributable application denial, not a kernel denial. An agent cannot choose a new URL or administrator method. |
| Bounded delegated and prepared work | Atomic per-attempt/global reservations before preparation or broker admission; durable external-dispatch intent and bounded output | Report reservation, actual use and unresolved debits with attempt identity. Cgroup limits alone do not bound trusted work or establish remote completion. |

Profile acceptance records allowed control cases and violations, immediate fork/exec, unrelated errors of the same syscall, enforcement-install failure and reader loss. Custom BPF-LSM policy, ActPlane and Actime are optional later profiles; their installed version/path must earn a separate denial coverage claim. No argv-based kill is labelled pre-effect denial.

Loss of required enforcement closes launches, quarantines affected broker channels and terminates affected attempts; it cannot undo prior effects. Diagnostic-reader loss preserves enforcement, marks evidence incomplete and closes new diagnostic-profile launches. Existing server attempts may finish under installed isolation with incomplete reports; robot delegation follows its finite grant/evidence policy. Trace loss counters and unavailable hooks remain visible.

## 3. Durable intent, recorder health and replay

Before first possible dispatch, persist operation ID, client request key/digest, instance/grant/context and immutable configuration in the local intent database. Dispatch only after a successful durable commit and fresh live checks. Storage failure rejects new operations. After recovery, unfinished intents are `OUTCOME_UNKNOWN`; neither database restoration nor a retry silently resends them.

For each producer, retain three distinct frontiers:

- `read`: copied from the producer into bounded recorder memory.
- `queued`: accepted into a bounded persistence batch; still volatile.
- `durable`: required files flushed/synced and their checkpoint committed to the database.

The writer orders recording-file persistence before committing the checkpoint; recovery excludes unsupported checkpoints/tails from authoritative results, preserves raw remnants for diagnosis and reports the gap. Storage durability means the selected stack honored its tested flush contract, not survival of arbitrary media failure. The recorder authenticates source channels and assigns origin labels; agent payloads cannot claim kernel/controller origin. A hash proves content identity, not trustworthy authorship.

The robot profile must supply maximum volatile bytes/records, maximum age since durable progress, heartbeat interval and maximum permitted continuation after health loss. These are required finite inputs, not inferred from queue capacity. A trusted writer reports its durable frontier separately from reader acknowledgement. Reader alive with writer stalled therefore exhausts the age/budget. Repeated heartbeats with an unchanged frontier do not establish progress while required records are pending.

Crossing either bound closes new experimental admission **and revokes existing experimental streams** through the normal urgent path. No arbitrary continuation is authorized by a healthy read cursor. Kernel/controller protection never waits for fsync; reserve transition-event capacity and still expose overflow. Continuous sample dispatch is asynchronous inside an already durable operation; it has no per-sample fsync. A crash can lose its tail, including the final loss marker. Unfinished intents, producer/session changes and last durable frontiers expose that uncertainty; successful control does not imply a complete episode.

Each attempt has a capture manifest: profile/configuration digests; producer identities and clock domains/error bounds; requested and actually retained streams; payload-versus-metadata policy; sequence ranges/gaps; durable frontiers; interventions; retention/redaction; and replay eligibility with missing reasons. Server and robot retain their own authoritative portions; export links them without converting remote claims into local facts.

Metadata-only is the default and supports inspection. V1 **execution replay** requires the instance activation boundary plus the complete retained input/model-output/configuration and execution/intervention prefix to the requested interval; a hash of missing content fails eligibility. This establishes the specified initial state and history, not deterministic physical reproduction. A partial mid-skill capture permits **event playback** with explicit gaps and unknown reconstructed state, not execution replay from invented state. Replay-only checkpoints are deferred. Fresh inference reproduction is a separate experiment. Replay runs under a no-device/no-live-credential profile with no command-service route. MCAP, OpenTelemetry and Rerun remain format/export/viewer integrations; none owns completeness or durability policy.

## 4. Enrollment, scopes and recovery

Enrollment is local-only while inhibited. On the robot's protected administrative Unix socket, `actryn device enroll request` creates a device key and outputs a CSR plus fingerprint. An operator checks that fingerprint on the physical/local console, signs it with the site's offline issuer workflow, then uses `actryn device enroll install` locally to install the certificate and selected site trust root. There is no unauthenticated network enrollment endpoint. `actryn device pair` verifies that enrolled device fingerprint and site chain before recording the connection.

Use an established X.509/mTLS implementation. Separate certificate scopes for deployment, attempt proposal, observation/readout and operator grant/rearm; the site's issuance policy prevents deployment identities requesting operator scopes. Local policy maps authenticated principals to ceilings; a valid certificate is not a grant. Proposed credential defaults: device certificate 30 days, operator session 8 hours, workload/deployment certificate 5 minutes. These are administrative design defaults, not physical response bounds. Workload certificates require renewal through the authorized issuer; offline expiry never extends automatically.

On connection, validate certificate time and local revocation state; derive a remaining session deadline on the robot clock. Session/grant lifetime cannot exceed credential/delegation validity. Credential renewal authenticates future requests; it neither extends an issued grant nor revives an expired one. Clock uncertainty or rollback closes new authorization and inhibits affected task authority. Local revocation immediately closes that principal's sessions and revokes its grants. A disconnected robot cannot instantly learn a remote revocation; short-lived delegation bounds this exposure. Site policy may shorten it.

Rotate keys through authenticated issuer approval plus local installation of new trust material while inhibited. Reconnect, rotation and re-enrollment never rearm. Lost/compromised administrator credentials require physical/local privileged recovery: inhibit, reconcile, retire all grants/sessions, replace trust roots/keys as appropriate and explicitly rearm under the new identity. Lost robot keys require re-enrollment, never identity copying from a process checkpoint. Decommissioning revokes credentials and removes local secrets only after required evidence export/retention.

## 5. Immutable releases and useful demonstrations

Use one initial `volnlabs/actryn` monorepo, with userspace, portable core, kernel, firmware and target boundaries. Independently version/promote server, robot and target artifacts. A signed immutable promotion manifest pins component/image/package digests; RPC/UAPI/features and gateway/manager transport/service configuration; exact kernel build/config/module; wire vectors and firmware; target hardware, policy/calibration; dependency/weight licenses and notices; build provenance; and exact conformance/qualification evidence. Missing or incompatible required entries fail preflight. CI consumes immutable artifacts built from pinned revisions, never an assumption that one shared commit makes every component compatible.

The same release system has independent eligibility: implement and accept the server alongside hardware/kernel work, using its own profile inputs. A server manifest can promote after its isolation/report/cleanup checks without robot D0/D1/D4 qualification. Target publication records supported exact tuples; it neither upgrades an installed robot nor qualifies another combination. A robot manifest pins a compatible server RPC range but keeps its exact qualified local tuple. A server update cannot silently update kernel, firmware or robot policy. Regression checks reconstruct manifests, reject deliberate mismatches, and exercise supported client upgrades/downgrades against a fixed robot tuple.

Trusted-stack updates require inhibition, downstream reconciliation and recovery access before staging. Gateway replacement first closes associated contexts/grants; service restart cannot silently restore them. The launcher and privileged observer remain trusted server components, even though their release is independent of robot qualification. Activate only the complete compatible tuple; power interruption leaves an inhibited recoverable installation. Firmware recovery follows the actual target mechanism. Reverting software creates fresh epochs/instances and reconciles; it cannot restore grants or reverse motion. Preserve evidence before schema migration; unsupported downgrade is rejected, not attempted destructively.

Two proposed operator stories define scope. The guided CLI presents the same stages with principal, target/profile, limits, generations and stable request handles; grant/rearm/activation remain separately authorized explicit actions. An interrupted guide queries retained identities before proceeding and never resends an uncertain effect or automatically rearms:

1. **Server diagnosis:** install, `actryn doctor --role server`, `actryn attempt prepare <agent-digest> --profile server-restricted`, then `actryn attempt start <prepared-attempt>` without a robot grant. A multimodal batch exceeds its memory budget while a child attempts forbidden host-device access and an unauthorized broker method. `actryn attempt inspect` distinguishes resource facts, failed OS access, broker-attributed denial, missing evidence and model/tool context; `actryn evidence export <attempt-id>` retains the report; cleanup leaves no descendants/credentials. Repeat with an unrelated open failure to prevent false denial claims.
2. **Repeated robot experiment:** install/doctor/enroll/pair; prepare the server attempt before local skill instance/grant/activation; acquire an encoder-indexed restrained-wheel observation; let the agent propose one bounded index step through a fixed skill; independently judge displacement using retained encoder/instrument readings. Trusted `operation.finish` requests `SKILL_FINISHED` closure; only a timely matched quiesce receipt releases the group for a second normally completed step under the same live grant. Preserve task verdict separately from closure/reconciliation, including target reached followed by failed handoff. Normal cancel uses `CANCELLED`; the kernel contract defines first normal reason and dominating grant/fault/expiry precedence. Also cancel by request key before the first ID returns, then deliver the delayed proposal. Next exercise grant expiry: observe `FAULT_LATCHED`, perform authorized `actryn robot reconcile`, explicitly `actryn robot rearm`, issue/activate a fresh grant and run a new operation. Deliver the old response and show rejection. Rearm alone never authorizes that new operation. This is the engineering fixture; the buyer demonstration adds a selected robot's repeated visual alignment task with independently measured final position. Its endpoint/task acceptance must be chosen before claiming customer usefulness.

Stress both stories: fill broker capacity with delayed/oversized and uncancellable replies, cancel/terminate/restart, and verify finite retained debits, no late publication and service for another already-admitted attempt. Exhaust staging capacity and inject allocation/preparation failures while A executes; verify rejection preserves A and accounting settles. Separately kill the daemon and expect owner-loss/expiry. Race key cancellation against allocation/commit/submission, crash after tombstone commit before acknowledgment, and stall storage during allocated cancellation. Delay successful-completion receipts and race finish/cancel/expiry; no next operation becomes eligible early.

An operator other than the author repeats both on a fresh second installation of the same supported target/profile, measuring install, diagnosis and recovery effort. This repeatability gate precedes expansion to a second controller; a successful controller port is different evidence. The robot story requires independent displacement evidence; if encoder hardware is unavailable, qualify an alternative instrument and revised task criterion before substituting it. Controller acknowledgement alone cannot supply task success. Hosted provider/model identity remains unselected; recordings can support software fixtures but cannot stand in for a live task-success benchmark.

Adoption order is standard facility → supported public API → narrow adapter → extracted source/fork. Extraction requires a semantic gap, pinned unit/license, retained assumptions, regression tests and named patch owner. These contracts customize the surrounding machinery without importing whole frameworks or copying maintained APIs unnecessarily.

Validation still required: selected-runtime launch ordering and policy tests, gateway authentication/lifetime/resource fixtures, persistence/crash fixtures, credential recovery, release reconstruction, model suitability and all target/physical measurements. This document resolves design choices; it is not evidence that those checks passed.
