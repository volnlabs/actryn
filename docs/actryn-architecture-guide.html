Start here: what are we building?

A system that makes repeated agent-driven robot experiments controllable, recoverable and explainable.

Imagine asking an AI agent to align a small rover with a marker. The agent looks at a camera image, reasons about the task and proposes a movement. That is the interesting intelligence problem. The product problem is larger: who permitted that movement, how old was the image, which controller received it, what happens if the agent disappears, and what evidence shows the rover actually moved?

Actryn is the execution and evidence system around that intelligence. It gives an operator a repeatable sequence: install, pair, observe, propose, admit, execute locally, interrupt, reconcile, rearm and inspect. A clever proposal is only one input. It cannot create its own permission or declare its own physical success.

Actryn Server

Runs the agent in a restricted Linux environment. Associates processes, resource pressure, model requests and tool calls with a particular attempt. Controls external requests through a broker. Produces useful diagnosis even when no robot exists.

Actryn Robot

Authenticates requests, runs reviewed local skills, checks observations and grants, controls the supported command route, handles interruption and retains evidence. Its essential behavior cannot depend on a cloud round trip.

The first version is deliberately specific

The selected execution class is an untrusted Python/native agent in a server container calling fixed, reviewed robot skills. A skill configuration supplies bounded parameters; it does not upload a new program into the robot. The first physical profile is a restrained wheel pair with no balancing or powered-holding requirement. A Shrike/RP2040-derived fixture is the engineering preference, but the complete hardware/kernel/firmware tuple is still a qualification decision.

The first demonstration uses hosted inference as its starting mode. The agent’s orchestration remains local to its server host; the model computation is remote. The particular provider, model version and measured suitability remain open. “Astra” alone is not a complete deployment specification.

The central invariant

Changing the model, process, deployment or behavior must not silently change who may command an actuator.

Linux, without the assumed background

The operating system is both a service provider and a protection boundary. We add a very small part to it.

Application, kernel, hardware

Your Python program normally runs in userspace: its own virtual address space with limited privileges. It cannot simply write into arbitrary device registers. To open a file, create a process, send data or request device work, it asks the kernel through a system call. The kernel checks permissions and invokes the relevant subsystem or driver.

Userspace application→ syscallLinux kernel→ driverHardware

A driver is kernel code that knows how to interact with a class of hardware. In our design, a controller backend additionally knows the particular robot protocol: which typed command becomes which bytes, what a receipt means and how to reconcile a queue.

A daemon is an ordinary long-running userspace service. The “d” in robotd or serverd is a naming convention, not a special privilege. A daemon can be unprivileged or carefully privileged depending on how it is launched. systemd starts and supervises services; it is not the motor-control loop.

Kernel module, kernel patch, Linux distribution

A loadable kernel module, commonly a .ko file, adds code to a running kernel. It runs with kernel privilege. A kernel patch changes kernel source and normally requires a matching build. A distribution combines a kernel with userspace packages, installation, service management and update policy. Adding our module does not require inventing a new distribution.

The first preference is an external module using supported exported interfaces on an exact qualified kernel. If a required lifecycle or interface is unavailable, a small justified patch or a different supported base may be necessary. An arbitrary module built for another kernel is not a supported artifact. Kbuild uses the target kernel’s configuration and build information. Linux external-module documentation

The custom kernel component is a confirmed V1 requirement. That is a product constraint. Whether it improves particular outcomes over a competent userspace gateway remains an experiment; “inside the kernel” is not automatically faster, safer or more secure.

File descriptors are handles, not identities

open() typically returns a small integer called a file descriptor (FD). It names an open kernel object for that process. read(), write(), poll() and ioctl() operate through such handles. An ioctl is a device-specific structured request, such as “query this endpoint” or “cancel this operation.”

Descriptors can be duplicated, inherited or passed to another process. Closing one copy is different from releasing the last reference. We therefore do not treat possession of a descriptor as permission to impersonate the registered robot runtime. The kernel also checks the referenced owner’s process lifetime and credentials.

The important danger of kernel code

A bug in an ordinary process can often be contained by the OS. A kernel bug can corrupt the host, bypass isolation or stop all progress. That is why inference, image processing, databases, downloads and arbitrary behavior code stay out of our kernel component. The kernel owns narrow authority and dispatch rules, not the whole application.

Who is trusted?

V1 assumes hostile unprivileged agents, delayed/replayed requests and component crashes. It trusts the host kernel, administrator, launcher, authority manager, selected backend, controller and required sensors. The gateway is not trusted to assert the caller’s identity. A compromised Linux kernel or administrator is outside this threat model.

This matters: a custom kernel module cannot protect the system against the kernel itself. A future hostile-host profile would need a suitably independent authenticated enforcing controller/domain and its own observation provenance. It is a different product contract.

One host or several?

The server can be a laptop or another supported Linux machine. The robot has its local computer and controller. A second Pi is possible if its measured workload fits; exactly two Pis is not a requirement. A single-machine simulator is useful but has no live actuator mappings or credentials. Co-located inference on a real robot needs separate interference qualification.

Example identities

Suppose attempt A proposes “perform the reviewed index-step skill” with request key K. The robot binds (A,K) to operation O and immutable digest D. If the reply is lost, the caller asks about (A,K). It does not send a new unrelated operation. The same key with changed arguments is a rejection, not an update.

The kernel-issued operation epoch includes device identity, controller boot/session and host runtime nonce. Controller boot identity has a specified durable counter requirement; a nonce alone is not the entire uniqueness argument. Counters do not silently wrap. Exhaustion, failed persistence or incompatible identity recovery inhibits output.

The server: isolation, attribution and a broker

The agent is allowed to be wrong. The environment must still know what it did and limit what it can affect.

Prepare first, execute last

  1. The trusted launcher allocates tenant/job/attempt identity and a dedicated cgroup lifetime.
  2. It prepares an immutable image/root filesystem, approved mounts, minimal devices, credentials and a per-attempt broker socket. It closes unrelated inherited descriptors.
  3. It installs namespace, UID, capability, seccomp, resource and network restrictions; attaches required enforcement and attribution.
  4. It creates a stopped task through the selected OCI runtime, checks the binding and readiness, then starts application code.

This ordering prevents “we began observing after the dangerous first instruction.” Untrusted image hooks cannot run early. If the runtime cannot establish the ordering on the selected version, that integration is unsupported. Containerd is the selected initial backend; we do not expose its unrestricted control socket to the agent.

Why use a broker?

The initial agent sandbox has no routable network interface. It calls named approved model/tool methods through an attempt-bound local Unix socket. The broker owns provider credentials, destination policy and request/output limits. The agent does not get an arbitrary “fetch any URL” interface, site credentials or robot admin keys.

This is also an accounting boundary. A container can be within its memory budget while causing expensive work outside it. The broker must reserve capacity before accepting or dispatching that work.

Attribution must survive names being reused

A numeric PID is not a permanent identity: Linux can reuse it after a process exits. Cgroup names/IDs also need a lifetime. The launcher records host boot, attempt, cgroup and process lifetimes before execution. Fork/exec descendants stay associated with that attempt; escaping the assigned cgroup is denied. Cleanup reaps the complete cgroup and revokes credentials.

Shared inference/GPU workers need request-level instrumentation. A host cgroup alone cannot tell which request caused every operation in a shared worker. A guest VM similarly needs a trusted guest collector for finer attribution than host VM activity.

A useful report says exactly what is known

“Attempt A exhausted memory” is different from “subprocess P had an open call fail.” An EACCES result does not identify the responsible policy by itself. Use policy_denied when the enforcing source supplies that fact; otherwise use access_failed or coverage_unavailable. Broker-origin rejection is an initial attributable denial source.

Required enforcement failure blocks launches and applies the declared quarantine/termination policy. Loss of a diagnostic reader does not remove enforcement; it marks evidence incomplete. Start with process lifecycle, pressure, CPU/memory, I/O and network metadata. Add probes only when they answer a concrete operator question.

Resources have lifetimes too

A queue limit is useful, but work does not stop existing when it leaves the queue.

Delegated work

Before broker admission, reserve per-attempt and global capacity for outstanding jobs, request/response bytes, retained output, deadlines and applicable token/provider budgets. Count queued, running, cancelling and unresolved work. Stream outputs into bounded buffers; excess output cannot become a tool proposal.

Example: the model call times out

The caller stops waiting. The provider might still be generating and charging. Returning the reservation immediately would let a loop repeatedly timeout and accumulate unbounded external work. Close publication into the old context, but keep the uncertain reservation until a verified outcome or an established provider-enforced bound settles it.

Persist external-dispatch reservations before sending work. On broker restart, restore unresolved reservations before new admissions. Do not resend them or declare the budget free because the old process disappeared. Corrupt/ambiguous accounting blocks new dispatch. This conservative rule can reduce availability; its purpose is to prevent crashes and cancellation from resetting the budget.

After completion, consumed provider budget remains charged for the accounting period. Only unused budget is returned after settlement. Retained response storage stays charged until actually consumed/deleted. If a method cannot enforce the promised provider-cost bound, it is unsupported in that bounded profile.

Preparing B while A is running

Behavior replacement temporarily holds more than the active behavior. Reserve capacity for active + staged + retiring instances, state, temporary buffers and bounded preparation work before constructing B. A failed activation leaves a finite-lived staged reservation; it is released only after cleanup finishes. Retiring A is charged until its handoff and callback/task teardown finish.

A normal “capacity exhausted” rejection leaves A untouched. A manager crash or out-of-memory death is different: it invokes owner-loss protection. We must not promise that A continues through an entire daemon failure merely because ordinary preparation happens off the control path.

Stopped prepared server sandboxes also reserve finite count, memory, image-storage and lifetime capacity. Failed start, abandonment or timeout revokes their credentials and releases capacity only after resources are actually reaped.

Resource separation is not a timing proof

CPU quotas, queue bounds and I/O limits make overload manageable. They do not establish a hard deadline for every driver, interrupt, cache miss or device interaction. Qualification measures interference from inference, image export, logging and diagnostics. PREEMPT_RT and timerlat can help investigate latency; neither proves our whole physical response contract.

Pairing, authentication and the gateway

Separate the right to install software, the right to propose a task and the right to grant motion.

Enrollment is deliberately local

While inhibited, the robot creates a key and certificate-signing request through its protected local admin socket. The operator checks the fingerprint at the device, uses the site’s offline issuer workflow and installs the signed certificate/trust root locally. Pairing then verifies that identity. There is no unauthenticated network enrollment endpoint.

A certificate establishes a principal under the site’s policy. Scope distinguishes device identity, deployment, workload proposals, readout and operator grant/rearm rights. A deployment credential cannot become an operator credential through a convenient API. Certificate validity is not a motion grant.

Why the gateway only relays ciphertext

gatewayd accepts network connections and forwards bounded encrypted streams. The established mTLS session terminates in robotd, which independently verifies the original client. The gateway cannot replace the caller’s name in an HTTP header and thereby obtain another principal’s rights. It holds no device/operator keys or kernel handles.

This reduces what the public relay is trusted to do. It does not remove all trusted parsing: the TLS implementation and bounded RPC decoder still run in the manager. Use established cryptographic/RPC libraries; do not invent a second signed-request protocol merely to create this split. State-changing TLS early data is disabled.

What if the gateway is compromised?

It can drop or delay traffic and deny network service. It cannot authorize a command by announcing a principal. Manager-side budgets constrain handshakes, decoders, sessions and queues even if gateway rate limits are bypassed. Control/closure capacity is reserved separately from bulk observation export.

The manager binds relayed sessions to the supervised gateway’s retained process lifetime, not a numeric PID or “last socket closed” assumption. Gateway exit/replacement closes its contexts and revokes associated grants through urgent kernel closure. Retained socket copies do not establish continued gateway ownership. Exact process-handle association and bounded detection remain implementation tests.

Disconnection is not one universal event

  • Ordinary agent/client disconnect: an already admitted skill may continue only under its installed continuation policy and original finite ceilings.
  • Gateway replacement or required authenticated-session liveness loss: affected contexts close and grants are revoked.
  • Manager death: kernel task-owner/deadline rules apply.
  • Whole-host loss: independent controller expiry is required.

A local operator can query, cancel, revoke, reconcile and rearm through the protected direct socket without the gateway, server or cloud. Remote cancellation is not guaranteed through a malicious relay. Forwarding a cancel message is not a cancellation receipt.

Expiry, rotation and lost keys

At connection, the robot checks certificate validity and local revocation state, then bounds session lifetime using its own clock. Renewal authenticates future requests; it does not extend a grant or clear a stop latch. Remote revocation cannot reach a disconnected robot instantly, so finite delegation limits the exposure. Clock uncertainty or rollback closes new authorization and inhibits affected task authority.

The design proposes administrative credential lifetimes of 30 days for devices, eight hours for operator sessions and five minutes for workload/deployment certificates. These are configurable policy defaults, not physical reaction times. Compromised/lost keys require inhibited local recovery, reconciliation, retirement of grants/sessions and authorized new trust material. Re-enrollment never resumes an old operation.

Basis: gateway and enrollment contracts.

One complete operation, from image to outcome

The proposal becomes an effect only after several independently meaningful boundaries.

  1. Install and preflight

    Verify exact artifacts, target policy, route closure, firmware/kernel compatibility and required evidence/limits. Installation starts inhibited. Pairing records identity, not permission.

  2. Prepare attempt and instance

    The launcher reserves attempt A before code runs. Robotd reserves capacity and constructs fresh state for reviewed skill S. The immutable configuration identifies S and its parameters.

  3. Authorize

    The separate operator/admin role issues a bounded pending grant for that principal, attempt, instance and group. Recovery checks and explicit rearm are distinct from activating the authorized instance. Neither a model nor normal client can issue these rights.

  4. Observe and infer

    The robot retains observation O with acquisition bounds and calibration. The broker binds model request, observations, configuration and response. Hosted inference produces a proposed task; it cannot rewrite O’s capture time.

  5. Bind durable intent

    The client already has request key K. Robotd reserves a robot operation ID and persists K, digest and parent intent outside the short registry lock. It then rechecks cancellation, identity, live grant and context before kernel admission.

  6. Execute a reviewed local skill

    Robotd turns the admitted task into fixed typed wheel-duty samples. The kernel checks the current owner, operation, generation, expiry, observation and installed numeric constraints. The agent never sends raw UART bytes.

  7. Dispatch locally

    The backend admits a nonblocking byte prefix into the UART driver under the authority ordering. The controller checks session/sequence/deadline and applies an eligible sample. A successful SAMPLE_APPLIED reports actual applied duty and controller time.

  8. Finish and reconcile

    The trusted skill executor asks for operation.finish with reason SKILL_FINISHED. The kernel closes local eligibility and performs the quiesce barrier. Only a matching timely receipt releases the group for another operation. A valid grant can remain usable.

  9. Judge the task separately

    An independent instrument judges displacement. “Target reached, but handoff failed” is possible. Store that combination instead of collapsing everything into “success.”

Inside our small kernel component

It owns the last enforceable host boundary for the supported controller, not the whole robot.

The typed boundary

The first command class is WheelDutyPair: signed integer left/right duty in permille. The representable interval is −1000 to +1000; the installed qualified ceilings may be far smaller. This is a numerical representation, not an approved power setting. Duty is not velocity. Wiring polarity, channel ordering and zero/disable semantics belong to the target profile.

The kernel checks fixed identities, ownership, generations, horizons, observation context, modes and limits. The manager/skill must also validate relevant geometry, contact and task preconditions. Passing fixed kernel checks is not a proof of collision-free behavior.

Why not just put a Python gateway before the driver?

A competent userspace gateway can do substantial validation. It is our comparison baseline. The custom kernel component additionally places effective authority and the supported byte-acceptance boundary behind a kernel-owned endpoint. A misbehaving client cannot become a raw writer simply by bypassing one RPC path, provided all alternate routes have actually been closed.

That last condition is crucial. Enumerate device nodes, controller sockets, ROS topics/services, raw buses, inherited descriptors, shared memory, debug/flashing paths, MMIO and controller autonomous modes. Protecting one advertised API while leaving another writer active does not establish exclusive authority. Root remains trusted under V1.

UAPI design: copy, validate, then act

The character-device interface separates administrator, runtime, acquisition and read-only event rights. The admin establishes pending grants and installed ceilings. Runtime calls consume existing permission; they cannot widen it or clear latches. Typical operations cover query, register, prepare/activate, submit, cancel/finish, revoke, reconcile and rearm. Exact layouts are still versioned implementation work.

Use fixed-width fields, lengths/versions, initialized padding, checked arithmetic and bounded copies. Reject unknown mandatory features, nonfinite values where applicable, invalid units/revisions and oversize requests. Copy userspace input into owned bounded storage; do not keep an agent-controlled pointer as a future motor command. Kernel pointers must not escape in responses.

Portable rules versus Linux glue

Portable Rust reducer

Given state, an event and time, returns new state and requested actions. No device I/O, RPC, database or privileged identity lookup. Bounded state and explicit failure paths allow focused testing.

Kernel integration

Obtains authenticated task identity and actual time, serializes mutations, manages references, handles callbacks and performs supported nonblocking device writes. This layer must establish Linux-specific correctness.

Shared Rust semantics with thin kernel glue are the preferred candidate. The exact target must pass abstraction/export/toolchain, synchronization and lifetime checks. A documented C fallback is allowed for a real support gap or disproportionate patch cost. We do not require two production versions merely to keep options open.

no_std means code does not use Rust’s standard library; it does not automatically mean “no allocation,” “no panic,” or “safe to run inside Linux.” The existing AxiomOS time queue, for example, allocates fixed-capacity storage during initialization. Extraction must inventory and adapt real behavior. The dispatch hot path must allocate nothing.

Why no programmable policy engine yet?

V1 uses fixed reviewed checks. eBPF probes and supported BPF LSM enforcement have bounded roles, but a new userspace JIT or programmable motor policy would add verifier, execution, helper and lifecycle obligations. Later predicates may only narrow fixed ceilings; they cannot take over owner transitions or clear a stop latch. Program tags alone do not bind all associated map/configuration contents.

Locks, workers and lifetimes

Two requests can arrive at the same time. The design must say which one wins and when that becomes true.

One authority mutex

A mutex gives one execution context at a time access to protected state. Our per-endpoint authority mutex orders effective grants, generation changes, operation eligibility, queue changes and each accepted UART byte prefix. The instant a close transition commits under this ordering is its linearization point: after it, new ordinary commands cannot become eligible.

The worker handles ordinary bounded events. An authorized urgent close takes the same mutex directly instead of joining the ordinary FIFO. Therefore the worker is not the only mutator; the mutex defines the shared order. No filesystem, network, model, allocation or blocking controller wait occurs while holding it.

Why not put STOP at the back of the queue?

Because a flood of ordinary work could delay it behind exactly the work it is intended to stop. Reserve fixed closure storage and bypass the ordinary queue for eligibility closure.

Callbacks leave bounded notes

A callback is code invoked when an event occurs, such as UART input or a timer. Some contexts cannot sleep. Timer/interrupt callbacks do not take the sleeping authority mutex. They capture bounded input or publish a pending closure and schedule work. The worker later handles the event in the appropriate context.

Pending closure slots merge monotonically: detach/fault dominates grant revoke, which dominates operation close. Old identities cannot overwrite a current close; weaker requests cannot erase stronger ones. Overflow of required closure storage escalates to fault rather than silently losing closure. The pending slot is a notification, not a second effective ownership table.

The worker handles at most one bounded event/frame-prefix write per lock acquisition, then releases it. Actual driver call duration and callback reentrancy still need inspection. “Nonblocking API” does not mean “zero execution time.” Mutex documentation; workqueue documentation.

Time decides at the actual transition

A callback might capture a receipt before expiry but get processed afterward. Recheck the actual robot clock when processing it. Expiry/closure wins at equality. A late successful receipt cannot clear a latched fault, reconcile a timed-out transaction or make another operation eligible.

Why FD close and PID numbers are insufficient

The kernel retains the original robotd thread-group leader’s task/PID identity, not merely its numeric PID. Runtime calls require the same group and credentials. A fork or passed descriptor does not transfer authority. Leader exit conservatively closes authority even if another thread or descriptor reference survives.

Robotd installs exec-denying seccomp before worker threads and authority registration, or synchronizes the filter across existing threads before proceeding. Replacing its executable is not a supported owner transition. Death checks occur before writes and periodically; detection is finite, not instantaneous. Controller expiry covers missing host progress.

References, RCU and unplugging

A reference count prevents an object from being freed while another context still uses it. RCU is a Linux technique for safely coordinating certain concurrent readers with object updates/reclamation; it is used here in lifetime checks, not as an authorization mechanism. Neither replaces the authority mutex.

On detach, first mark the endpoint detached and close eligibility. Stop new callback scheduling. Outside the authority mutex, cancel work/timers and quiesce the actual driver’s callbacks while retaining the binding reference. Only then release objects. Old descriptors remain detached; they cannot magically attach to a replacement device. There is no assumed universal serdev “all callbacks finished” API.

Runtime power management must not suspend the active transport. Verify the parent driver honors the pinned usage reference. Planned suspend inhibits/reconciles first; resume, PM errors or clock discontinuities require fresh recovery. The MCU’s expiry clock must keep working when Linux does not.

UART bytes, queues and the controller

Authority can close locally while already transmitted work still has consequences.

What serdev buys us

The candidate fixture uses a dedicated UART bound to a kernel serdev backend. Successful exclusive binding excludes a normal writable TTY for that path. The target must also remove console/debug use and audit pinmux, MMIO and other routes. Binding failure leaves motion inhibited; it must not silently fall back to a userspace TTY writer.

The final enforceable host boundary is acceptance into the UART driver’s buffer, not the final physical bit. write_wakeup means “ready for more data,” not “the prior frame drained.” A drain is still not a controller-applied receipt. The proposal deliberately waits for the current sample’s actual controller receipt before sending another sample.

One started frame, one replaceable unsent sample

V1 allows one started immutable command frame and one latest-value sample that has not begun transmission. A newer eligible sample may replace the unsent one. Arbitrary trajectories and action chunks are unsupported. This intentionally restricts throughput; it is not a promise of 500–1000 Hz host dispatch.

Cancellation in the middle of a frame

  1. Close ordinary eligibility under the authority mutex.
  2. Drop the wholly unsent sample.
  3. If a frame has started, finish only its exact remaining bytes with original identities and expiry, within the recovery bound.
  4. Send the named quiesce barrier without waiting for the old sample receipt.
  5. Accept reconciliation only from the matching timely controller response. On stall/error/timeout, latch fault and rely on independent endpoint expiry.

The old partial frame can still cause a residual effect before its original expiry. That is part of the contract and must be measured. We do not insert stop bytes into an unfinished frame or promise that flushing erases transmitted bytes.

The inspected Shrike v1 codec uses counted SYNC/version/type/length/payload/CRC framing, not COBS. A truncated message can consume following bytes as payload. Even a CRC failure would not by itself prove prompt stop delivery. The new fixture wire v2 is explicitly incompatible with v1; old tests provide lessons, not proof of compatibility.

What travels in wire v2

As applicable, messages carry device identity, controller boot/session, host runtime nonce, grant generation, operation, stream, sequence and transaction. Commands carry typed values and absolute controller-clock expiry. Unused fields have canonical values, not wildcard meanings. Receipts echo the identities and state they actually establish.

The controller increments a durable nonwrapping boot counter before accepting handshakes, creates fresh per-boot sessions/challenges while inhibited, and consumes rearm challenges once. Failed/ambiguous persistence inhibits output. A sample cannot reopen a retired operation. Reinstalling firmware cannot silently reset identity namespaces.

CRC detects corruption, not an attacker forging traffic. The initial physical link is trusted against hostile injection. A hostile-bus profile would need a different authenticated-link contract.

Absolute expiry beats a renewed timeout

A stale buffered command might arrive very late. If its arrival starts a brand-new timeout, it can outlive the original grant. We instead derive an absolute controller deadline conservatively from the robot’s remaining authorization. The controller checks it before application and throughout execution; receipt and delayed arrival never renew it.

A successful SAMPLE_APPLIED is emitted after the controller sink/register update succeeds, with actual applied duty and application time. This establishes a slew baseline. Parsed/queued ACK is insufficient. Rearm and matched quiesce establish a disabled-zero baseline. These remain controller facts, not an independent measurement of motion or electrical disable.

These are separate operations because they answer different questions.

Endpoint state names describe the authority lifecycle: INHIBITED, READY, ACTIVE, REVOKING and FAULT_LATCHED. Candidate PREPARED state is separate: B may be prepared while A runs without already owning motion authority.

Finish races with cancel

The first matching normal close request fixes its normal reason. A duplicate request does not create another barrier or relabel history. Broader grant revoke, expiry and fault still dominate eligibility. A skill reaching its target does not free the actuator group by itself. The next operation waits for a matching timely quiesce receipt.

Cancel before the first reply

The client exposes request key K before sending. If no operation ID comes back, query/cancel K. Robotd orders allocation, cancellation and final kernel submission under a short per-key lock; storage I/O happens outside it. A terminal-wins database revision prevents a delayed intent commit from overwriting an earlier cancellation.

If K has no operation yet, create a bounded terminal tombstone and persist it before claiming KEY_CANCELLED_DURABLE. A delayed first proposal cannot cross that fence. If K already has an operation, urgent kernel closure does not wait for the cancellation record to reach disk. Report pending durability and actual local/controller closure separately.

Do not evict a live tombstone to accept more work. Exhaustion rejects new admissions, with reserved capacity for cancellation of existing operations. After a manager crash, retired namespaces cannot create effects even if a cancellation commit was lost. Unfinished durable operations remain OUTCOME_UNKNOWN until reconciliation establishes more; they are not automatically retried.

Replacing behavior

Prepare B outside the control path with reserved capacity. Verify the expected generation and its pending grant. Close A, reconcile downstream work, then publish B with a new generation and fresh state. A delayed callback from A cannot mutate B. Selecting an older artifact also creates fresh state; “rollback” is not restoration of old process memory or physical position.

Takeover follows the same rules

A teleoperator does not bypass the authority gateway simply because a human moved the joystick. Human takeover requires owner transition and the controller-specific handoff evidence. A remote stop request is not the independent physical protective mechanism. Homing, braking, holding, disabling torque and removing power are distinct actions with different physical consequences.

  1. Prepare an attempt, fresh skill instance and finite operator-authorized grant.
  2. The reviewed local skill executes an admitted operation.
  3. Trusted finish closes it; a matched timely barrier reconciles the controller.
  4. A distinct operation may use the still-valid grant. Independent measurements decide each task’s physical outcome.

Normal completion does not require pretending a fault occurred or automatically rearming.

Evidence, datasets and replay

An inspectable outcome preserves disagreement and uncertainty instead of hiding them in one success flag.

Different components originate different facts

The agent can explain its reasoning. The kernel can report admission and local dispatch. The controller can report its defined application/quiescence facts. An instrument can report physical measurements. Each event retains producer identity and lifetime, monotonic sequence, local clock domain, configuration identities and relevant attempt/operation/observation references.

Trace IDs connect records; they do not prove causality or completion. A content hash establishes identity of bytes, not truthful authorship. Broker lineage is server-attested, not proof the model attended to a particular image or protection from a compromised server.

SQLite

Stores durable parent intents, operation/request-key records and indexes. Critical parent intent is committed before effects. It is not queried synchronously inside the kernel dispatch lock.

MCAP + optional viewers

Records timestamped events and sensor streams asynchronously. OpenTelemetry helps correlate spans; Rerun can inspect exported data. These tools do not define our authority or evidence meanings.

The three recorder frontiers

  1. Read: copied from a producer into memory.
  2. Queued: accepted into a persistence batch, still volatile.
  3. Durable: required recording files persisted and the matching checkpoint committed.

The file data is persisted before SQLite records the checkpoint. A healthy reader with a stalled disk is not healthy recording. Required profile limits bound volatile bytes/records, pending age, health interval and permitted continuation after health loss. When age or capacity crosses the bound, close new admission and urgently revoke existing experimental streams. Protective closure never waits for fsync.

Continuous samples are not individually fsynced. A crash can lose the tail, including a final “records dropped” event. Unfinished intents, producer changes and last durable frontiers expose uncertainty. There is no promise of zero loss under arbitrary media failure.

Keep four outcome dimensions

Admission may be allowed/clamped/rejected. Delivery may be unsent/partial/controller-applied. Lifecycle may be closed/reconciled/unknown. Physical evidence may be observed/unconfirmed. A clamp retains both requested and admitted values. A learned failure classifier adds an estimate with model/version and uncertainty; it cannot overwrite a trusted fault or turn a censored attempt into planner failure.

Replay has two meanings

Event playback reconstructs the recorded timeline, including gaps. Execution replay runs captured inputs through a known fresh skill state. V1 execution replay requires the activation boundary and the complete ordered prefix of relevant inputs, model outputs, configuration, clamps, interventions and controller outcomes before the requested interval.

A clip beginning halfway through a task cannot invent the missing state. Without the prefix, permit inspection with state-unknown labels, not execution replay. A hash of a missing image cannot replace that image. Replay-only checkpoints are deferred.

Replay runs with simulator identity and no live keys, devices or command-service route. An agent’s --replay flag is not a security boundary. Fresh remote inference is a different experiment; recorded outputs are used for reproducible software investigation. Software replay does not reproduce the physical world.

Privacy and useful datasets

Default capture is metadata. Full prompts/images/model outputs require explicit site policy, retention and redaction. A capture manifest records what was requested, actually retained, missing and replay-eligible. Useful robot episodes contain synchronized observations plus proposed, admitted and executed history, interventions and uncertain outcomes—not merely camera footage.

Reuse native semantics before requiring new firmware

An existing controller need not adopt fixture v2’s exact bytes if its native interface establishes the same required facts: exclusive typed dispatch, nonreused operation identity, stale retirement, original finite authorization horizon, bounded closure, meaningful receipts, reboot inhibition and independent host-loss response.

If an obligation is missing, compare a justified backend/firmware adaptation with rejection. Do not silently downgrade after a failed handshake.

What must survive Linux stopping?

The controller or sufficiently independent component must enforce expiry and the declared host-loss response without Linux progress. Another daemon on the same frozen host cannot provide that guarantee. The restrained fixture expects a qualified zero-drive/output-disable response; coast and residual motion require measurement.

Braking dissipates motion, holding actively sustains position, torque disable stops commanded drive, and power removal changes the electrical supply. These are not synonyms. A balancing robot or loaded arm may need an independent stabilizer rather than immediate disable; V1 makes no such general claim.

FPGA versus simpler protection

A small FPGA gate may provide envelope/PWM/interlock functions, but its watchdog depends on top-level logic and a real oscillator. Rewriting that logic requires renewed qualification. A discrete watchdog can be simpler for a specific silence-detection requirement. Choose against the actual fault model and measured electrical response, not visual architectural completeness.

A silence watchdog cannot by itself detect an MCU that keeps sending plausible-looking but wrong commands. Qualify the mechanism, firmware and wiring together. Human protective intervention must have a distinct route and meaning from a remote CLI stop.

Simulation, fixture and mobile robot are different evidence

Start with deterministic software fixtures. Then instrument restrained motors. Then qualify the named assembled robot and useful task. A fixture without encoders needs a qualified independent optical/electrical measurement and appropriate task criterion before substituting it into the demonstration. An always-unconfirmed motion cannot become a successful-task metric.

Updates and the operator workflow

Installing code, publishing behavior and granting physical authority are three different acts.

Three update classes

  1. Application deployment: place an immutable agent image or skill configuration on disk. It gains no authority.
  2. Behavior activation: prepare a fresh instance, consume an operator-authorized grant and perform any required handoff before publication.
  3. Trusted-stack upgrade: change manager, adapter/backend, kernel, controller firmware or related trusted configuration. Inhibit and reconcile first; preserve recovery access; stage and activate a complete compatible tuple.

A power interruption during a trusted update must leave an inhibited, recoverable installation. Firmware recovery uses the actual controller’s mechanism. Gateway replacement retires its sessions/grants; a service restart is not transparent authority continuity. Server launchers and privileged observers are trusted components even though their releases are independent of robot qualification.

Software rollback selects artifacts, not physical history. It creates fresh epochs/instances and requires reconciliation; it cannot reverse motor motion, restore grants or resume old state from a process checkpoint. Preserve evidence before schema migration and reject unsupported destructive downgrade paths.

How implementation would proceed

For a kernel beginner, the most useful first exercise is to make the rules testable before attaching motors.

Portable logic first

Extract a small authority transition core from the relevant AxiomOS logic. Document invariants, capacities and error outcomes before adapting types. The core receives explicit time/events and returns decisions. It does not look up a PID, block on a controller or write a file. A conceptual shape is:

// Teaching pseudocode; not the final ABI or compilable product code.
decision = step(current_state, event, robot_time)

if decision.requests_dispatch:
    kernel_glue.recheck_current_owner_and_deadline()
    kernel_glue.accept_bounded_prefix_under_authority_lock()

if decision.requests_close:
    kernel_glue.close_eligibility_in_the_same_order()
    kernel_glue.schedule_bounded_downstream_reconciliation()

The sketch omits real synchronization and cannot be used as a proof. In particular, all eligibility and byte-acceptance transitions share the actual authority ordering; a separate unchecked gap between validation and dispatch would be wrong.

Then establish the exact Linux integration

Choose the release kernel/configuration and toolchain. Check that required Rust abstractions and exported functions are available for the module. Rust’s development-tree support is not evidence that a board kernel supports the same APIs. If a justified C fallback is selected, retain the semantic contract and independent fixtures.

Kbuild builds kernel objects; Cargo can build/test the portable userspace core, but Cargo success does not build the kernel module. Kernel headers/configuration, exported symbols and compiler/toolchain compatibility all matter. BTF describes kernel types for tooling such as BPF; CO-RE adapts certain structure accesses, not missing hooks or changed semantics.

Bind the chosen device and inspect callbacks, buffer acceptance, runtime PM and teardown. Device Tree describes board hardware and bindings on relevant platforms; an overlay cannot prove the chosen UART pins are free of console/debug writers. Begin with an inert endpoint emulator, not powered motion.

What a customer would buy—and what remains unknown

A technically interesting architecture is not yet a repeatable product.

The buyer hypothesis is a robot-learning or agent team repeatedly running bounded experiments and losing time to installation, intervention and diagnosis. The proposed useful workflow is repeated visual alignment on one selected mobile platform. The restrained wheel experiment is an engineering gate, not by itself proof of buyer value.

The deliverable includes operations

A supported configuration includes preflight, pairing, configuration checks, SDK/CLI, clear rejection reasons, cancellation/recovery/rearm, diagnostic bundles, updates and an acceptance process. The founder should not have to personally interpret every failure or wire every installation.

Measure successful attempts per hardware-hour, operator interventions per attempt, install effort, time to explain a failure, recovery time and second-installation changes. Preserve unknown/censored outcomes and intervention history when calculating task success. A model benchmark score does not approve an actuator profile.

Open core is an option, not the source of demand

Public interfaces and conformance material make integration easier. Supported profiles, qualified integration, updates and support can be commercial offerings. A working glossary

Definitions in the context of this project. Follow the chapter links when a word needs its full contract.

ABI
The binary layout and calling convention two components must agree on. Our kernel interface uses explicit sizes and versions so a client cannot silently reinterpret bytes.
Admission
The decision that a particular request is currently eligible under identity, authority, resource, context and fixed-limit rules. It is not proof of physical success.
Artifact
An immutable versioned image, configuration or binary identified by digest. Installing it does not create a running instance or a grant.
Attribution
Binding an event or resource use to its actual producer and attempt lifetime. A claimed trace ID alone cannot establish that binding.
Attempt
One launcher-originated agent run, including its sandbox, identities, policy and evidence. Retained external-work accounting can outlive its processes.
Barrier
An identified protocol operation establishing the endpoint’s declared ordered state after earlier work. Its receipt means only what that endpoint contract specifies.
BPF / eBPF
Linux’s programmable mechanism used here for selected observation and supported security hooks. It is not the sandbox manager or our whole robot authority system.
BPF LSM
BPF programs at supported Linux Security Module hooks. Such hooks may deny operations, but they do not automatically interpret a robot’s typed motor protocol.
BTF / CO-RE
Kernel type information / Compile Once–Run Everywhere relocation support for suitable BPF programs. These help structural compatibility, not unavailable hooks or changed semantics.
Broker
Trusted service that performs named external model/tool calls for an attempt, owns credentials and keeps lifetime resource accounting.
Callback
Code invoked for an event, such as received bytes or a timer. Its execution context determines what locking or blocking is permitted.
Capability
A scoped permission. Linux process capabilities split traditional privileges; Actryn grants describe a different, robot-specific authority contract.
Cgroup
A Linux process group used for resource control/accounting. Its identity must be scoped to a lifetime; shared downstream work requires separate attribution.
Clamp
Reduce a request to an allowed value under declared rules. Preserve the original and applied values; revalidate the result and report the change.
Clock mapping
A bounded relationship between host and controller clocks, including uncertainty and drift. It supports conservative absolute expiry conversion.
Controller
The endpoint that interprets commands and drives the declared low-level behavior. It may be an MCU, vendor controller or another explicitly supported implementation.
Daemon
A long-running userspace process. The name itself says nothing about privileges or authority.
Deadline
The time after which work is ineligible. Checking the clock is essential even if a timer callback is delayed.
Device Tree
A hardware description used on relevant platforms to bind devices and drivers. It does not establish that wiring, pin use or physical response is qualified.
Digest
A content hash identifying bytes. It does not by itself establish trusted authorship, licensing, suitability or authority.
Dispatch
Accepting eligible command bytes at the final enforceable host boundary. It is distinct from downstream application and physical motion.
Driver
Kernel code mediating hardware access. Our endpoint backend also implements the selected controller protocol and receipt meanings.
Epoch / generation
Identity separating successive lifetimes or ownership revisions. Old work cannot become current simply because a process or device restarted.
Evidence frontier
How far a stream has been read, queued or durably persisted. These are different positions, with different crash-loss implications.
FD
File descriptor: a process-local handle to an open kernel object. Copies and transferred references do not establish the registered runtime owner’s lifetime.
FIFO
First-in, first-out queue. Ordinary FIFO submission must not force urgent eligibility closure behind a flood of commands.
Firmware
Software on the controller or another device. Updating it changes the trusted endpoint tuple and requires the defined recovery/qualification process.
Freshness
Eligibility based on the age and validity of retained observations/context. New transport receipt or inference completion does not refresh sensor acquisition.
Grant
Locally enforced bounded permission for an identified principal/instance/group and lifetime. Installation, authentication and rearm are not substitutes.
Hot path
Code executed for frequent timing-sensitive work. It needs bounded work and no allocation or blocking storage/network waits under the authority lock.
Idempotency key
A stable request identity used to recognize the same intended operation across retries. It does not promise exactly-once physical effects.
Inhibited
The state in which physical task activation is disallowed until required configuration/recovery/rearm conditions are met.
Instance
Fresh runtime state of a reviewed skill under an immutable configuration. Reusing an artifact creates a new instance rather than reviving old state.
ioctl
A device-specific structured request through a file descriptor. Our ioctl meanings belong to the versioned UAPI, with validation at the trust boundary.
Kbuild
The Linux kernel build infrastructure. Building portable Rust with Cargo does not by itself produce a compatible kernel module.
Kernel module
Code loaded into the kernel, normally as a .ko artifact. It shares kernel privilege and must match the supported build/configuration.
Linearization point
The ordered instant at which a concurrent operation becomes effective. Our local closure point is a protected authority-state transition, not a physical stop measurement.
MCAP
An existing recording format used for timestamped events and sensor data. It does not define authority, durability policy or physical truth.
Monotonic
Progressing without going backward within its stated domain. Clocks, counters and transitions still need explicit restart, overflow and uncertainty rules.
mTLS
Mutual TLS: both ends authenticate using certificates. In this design it terminates in the trusted manager, through an untrusted encrypted relay.
Mutex
A mutual-exclusion lock. It orders protected state changes; it does not automatically prove how long acquiring or holding it takes.
Namespace
A Linux mechanism giving processes separate views of resources. Actryn also uses identity namespaces; those are a distinct conceptual use of the word.
no_std
Rust code without the standard library. Allocation, panic paths, dependencies and Linux compatibility still require inspection.
OCI
Standards for container images/runtime behavior. Our selected runtime/configuration must still prove the prepare-before-start security ordering.
Operation
A durable robot-allocated identity for one intended effect, bound to a stable external request key and immutable digest.
Outcome unknown
Evidence is insufficient to conclude what happened. Recovery must retain this uncertainty rather than automatically retrying or declaring success.
Owner
The principal/runtime lifetime whose grant is currently effective for the supported actuator group. Effective ownership is kernel-authoritative.
PID / task lifetime
A PID is a reusable numeric name; the retained process/task lifetime distinguishes the actual owner from another process later using that number.
PREEMPT_RT
A Linux real-time configuration direction that can change scheduling/latency behavior. It does not independently qualify Actryn’s end-to-end physical deadlines.
Publication
Making a prepared, authorized instance/grant effective at a defined ordered boundary after required handoff. It is different from writing files to disk.
Quiesce
Ask the endpoint to close named work, remove pending task commands and enter the declared output state, then report that state through the protocol.
RCU
Read-Copy Update, a Linux concurrency/lifetime technique. It supports safe specified read paths; it does not itself confer authority or replace required locking.
Rearm
Explicit authorized recovery action after required checks. It cannot resurrect an operation or supply a missing grant.
Reconciliation
Establishing the declared downstream state using actual endpoint evidence. Local intent to stop is insufficient.
Reducer
A bounded function transforming explicit state and events into new state and requested actions, separate from platform I/O and synchronization.
Refcount
A count retaining an object while users/callbacks still hold references. Authority revocation and memory reclamation are separate questions.
Reservation
Capacity charged before accepting work and retained until the work/buffers actually settle. Timeout or process death cannot automatically erase external consumption.
Retirement
Permanently ending eligibility for an operation/session/namespace so late commands cannot reopen it.
RPC
Remote procedure call: structured messages invoking an API across a transport. Successful delivery does not imply authority or completion.
SAMPLE_APPLIED
The controller’s successful command/output-state update with identities, value and time. It is not an independent observation of motor motion.
Seccomp
A Linux syscall-filtering mechanism. Here it helps constrain agents and prevents exec-based replacement of the registered manager owner.
Serdev / UART
Linux’s serial-device framework / an asynchronous serial hardware link. Buffer acceptance, wire transmission and controller receipt are separate events.
Slew limit
A bound on how quickly a commanded value may change. Its baseline uses actual controller-applied value/time, with bounded elapsed-time credit.
Stop latch
A persistent inhibition condition in the supported lifecycle. A delayed success message or credential renewal cannot clear it.
Tombstone
A retained terminal record for a cancelled request key, including a key cancelled before any operation ID was returned.
Trusted computing base
The components whose correct behavior the stated guarantees depend on. Moving code behind a different filename or trait does not automatically remove it.
UAPI
Userspace API of the kernel component, including versioned binary requests and event meanings. It is separate from the network RPC schema.
WCET
Worst-case execution time under a justified bound and assumptions. The largest observed timing in a test campaign is not automatically WCET.
Workqueue
Linux mechanism for scheduling work in suitable worker context. Timers/callbacks may schedule work rather than sleeping or taking the wrong lock.
Zero-copy
Avoiding some data copies through shared buffers. It does not eliminate ownership, access control, expiry or lifetime problems.

Check your mental model

The module accepted a write. Did the robot move?

No. That may establish only local buffered bytes. Controller application and independent physical observation are separate later facts.

Can a valid certificate command the motors?

Only through the authorized interface with an effective bounded grant and all current checks. Certificate validity alone is not motion permission.

If the model request times out, is its resource reservation free?

No. The provider may still be running. Close the old publication context, retain unresolved accounting and settle it through established evidence.

Does rearm restart the interrupted task?

No. It neither restores a retired operation nor issues authority. Recovery and fresh authorized work are distinct.

Why can a normal completed skill run another operation without rearm?

Normal finish closes and reconciles one operation. If the grant remains valid and no fault occurred, another distinct operation can be admitted under that permission.

Why is a self-contained Rust core not a proof?

Shared code reduces divergence, but can carry a shared logic error. Independent expectations plus Linux integration/race/lifetime tests and physical evidence answer different questions.

## 1. Recommendation and design brief

Build **Actryn Server** and **Actryn Robot** around one operator CLI and a shared contract. Keep one initial product monorepo, release a small custom Linux authority component as its own artifact, and distribute hardware support as versioned target packages. Server, robot and target artifacts have independent promotion gates. Keep AxiomOS as a source of implementation experience and regression cases; extract its authority and lifecycle logic without bringing its boot, memory, filesystem or scheduler stack into the product.

The product is a repeatable operation: install, pair, observe, propose, admit, execute locally, interrupt, reconcile, rearm, inspect. Server-only installations must also be useful: a team can run an isolated agent attempt and explain its Linux resource consumption and denied operations without owning a robot.

User requirements carried into this design:

- Execution and authority remain local to the robot; model inference may be remote.
- Generated applications cannot obtain raw actuator access or enlarge their own grant.
- Installation works on an existing supported Linux distribution.
- Replacement, retries, crashes, controller queues and physical uncertainty are explicit parts of the contract.
- Upstream projects are assessed for a specific capability; adopting an entire framework is not the default.
- The first supported physical configuration and recurring customer workflow remain narrow.

Working assumptions: one commercial robot-learning/agent team as the buyer hypothesis; one operator-managed site; one wheel-pair ownership group; a restrained fixture before an assembled rover; a hosted model for the first demonstration. These are recommended starting choices, not confirmed equipment or measured inference suitability. The specific hosted provider/model remains unselected; “Astra” is not an API or model-version specification. TurtleBot3/OpenCR is a comparison candidate, not selected equipment.

**Selected V1 execution class:** untrusted Python/native agent code runs in a server OCI sandbox. It invokes reviewed, release-built native skills in `actryn-robotd` using bounded typed proposals. A robot behavior artifact is immutable skill configuration referencing one of those fixed skill IDs, not uploaded executable code. Instance state belongs to `actryn-robotd` and resets on activation. Generated robot-local code, dynamic plugins, live model/skill weight replacement and physical checkpoint restore are unsupported in V1.

The initial restrained-wheel profile requires no active balance or load holding. Its declared host-loss response is controller-side torque disable through the named electrical mechanism; braking distance and residual motion must be measured. This does not qualify an arm, balancing robot or humanoid. A later active-stabilization profile must separately assign surviving control/protective authority and qualify its transitions.

**Confirmed user decision:** a custom Linux kernel component is mandatory in the first release. The selected mechanism is a small authority driver and one exclusive controller transport backend. It governs ownership, fixed admission, dispatch and the protocol facts needed to validate handoff; it does not run arbitrary agent code. The historical direction is recorded in the [context brief](../../../../docs/proposals/axiomos-context-2026-10-11.md). Kernel inclusion is a product requirement, while superiority over the userspace baseline remains a hypothesis to measure.

### Alternatives considered

| Approach | What it buys | Cost / reason for decision |
|---|---|---|
| **Selected: our kernel authority component plus Linux userspace services** | One kernel-owned publication/dispatch boundary, existing Linux installation, separable server product | Requires exact kernel builds and a narrow supported transport; privileged Linux and downstream controller remain trusted |
| Userspace authority gateway on stock Linux | Smaller maintenance surface and a strong comparison baseline | Does not satisfy the required kernel component; retain as a measured baseline and reference model |
| Build a distribution around a complete upstream robotics/agent platform | Faster access to that platform's integrated features | Imports its authority, lifecycle, dependency and update assumptions; adapt only if its semantics fit better than our small core |

Do not fork a dependency merely to call it ours. Our ownership comes from the interfaces, integration, guarantees, support and evidence we maintain. A proven library may remain an ordinary pinned dependency; source extraction needs an explicit advantage over using its public API.

```text
    ros2/                   # only for a selected ROS controller profile
  targets/<target-id>/<revision>/
    manifest.yaml           # complete compatible hardware/software tuple
    command-paths.md         # all routes to protected outputs
    endpoint-contract.yaml
    wiring/
    qualification/          # instruments, procedures and acceptance definitions
  firmware/shrike/           # only firmware maintained for a supported target
  evidence-manifests/        # hashes/references; no implied physical PASS

  packaging/{deb,systemd}/

```

Dependency direction: schemas/contracts → services/SDK; portable core/wire → selected kernel/userspace/firmware integrations; canonical kernel UAPI → checked userspace client. The portable reducer returns decisions/actions and performs no I/O. Linux glue alone owns synchronization, task references, queues and device dispatch. Kernel builds cannot depend on Python, RPC libraries or daemon internals. Reuse wire code in firmware only when actual platform/allocation constraints fit; otherwise preserve golden vectors across implementations. Target manifests remain declarative, without arbitrary install hooks.

Kernel UAPI is canonical in `kernel/include/uapi/linux/actryn.h`; generated bindings and CI detect drift. Build immutable component artifacts from pinned source revisions, then promote **server**, **robot** and **target** artifacts independently. Promotion manifests record source, binary, vector, configuration, dependency and evidence digests. A target artifact declares supported exact tuples; publishing it neither upgrades an installed robot nor qualifies an untested combination. A server security fix need not wait for physical robot qualification. A single repository or shared commit never implies a lockstep rollout, and kernel-internal APIs are not assumed stable between builds.

Permit a single-machine developer/simulator profile, with no live actuator device mappings. Co-locating inference and motion on a physical robot is a separate resource-interference qualification, not a packaging checkbox. ### Processes and privileges

| Process / component | Responsibility | Authority |
|---|---|---|
| `actryn` | Human/automation client, diagnosis and offline evidence inspection | User credential scope only; no hidden motion or deployment privilege |
| `actryn-serverd` | Attempt orchestration, model/tool correlation, scoped robot client, evidence index | No raw devices, BPF loading or unrestricted container-engine socket |
| Restricted host helper | Server launch or robot operator administration, in separately scoped service roles | Protected authenticated local interface; caller-to-attempt/policy authorization; no caller-selected ownership, arbitrary descriptors, host command or credential paths |
| `actryn-observer` | Attach/read approved Linux probes; emit attribution and loss records | Profile-specific loading privileges; agent cannot submit BPF or access writable maps |
| Agent attempt | Run Python/native tools/model client | Its sandbox and bounded proposal channel only |
| `actryn-gatewayd` | Public network listener and bounded encrypted-stream forwarding to the manager | Separate unprivileged UID/service; no client-authentication authority, device/operator keys, kernel handles or raw controller access |
| `actryn-robotd` | End-to-end authentication, bounded typed RPC, skill preparation/state, native skills, durable intents, kernel requests and evidence export | Sole registered runtime kernel owner within installed ceilings; separate local admin role remains; no raw controller access, arbitrary code loader or forged handoff receipts |
| `actryn_authority.ko` + selected backend | Sole effective ownership, grant generations, fixed validation, publication, transmit queue and controller protocol | Kernel-resident final host dispatch boundary; direct controller binding excludes normal userspace writers |
| Sensor/control component | Produce qualified observations or execute a local policy | Narrow read/data interfaces; any command output still traverses the gate |
| Controller / protective equipment | Declared downstream execution, expiry and host-loss behavior | Independent of server and host application progress where the profile requires it |

The gateway is outside the authority trust boundary. It relays encrypted streams; established mTLS terminates in `actryn-robotd`, which verifies the original principal and attempt binding. Forwarded identity headers are never authorization. The TLS library and bounded RPC decoder remain trusted in the manager; this split does not remove every network-facing parser from the trusted system. Manager-side connection/handshake/decoder limits apply even if the gateway ignores its own limits. The [platform contract](../../architecture/platform-release-contract.md#robot-network-gateway) fixes lifetime, cancellation and recovery behavior.

The robot daemon handles management, preparation and persistence in userspace; it does not own a competing grant table. The kernel owns the effective grant and serialized dispatch state. A selected kernel backend binds the first controller transport. A native controller protocol may qualify through a named exclusive kernel backend and the semantic conformance map in §7; it need not adopt the fixture's wire encoding. A future vendor/ROS worker can only offer the same enforcement claim if its actual path passes such an integration; otherwise it is a separately labelled userspace-adapter profile. A worker holding raw actuator access remains trusted, even in another process.

The V1 threat model includes hostile unprivileged agents, delayed/replayed requests and component crashes. It trusts the host kernel, administrator, launcher, authority daemon, adapter, controller and required sensors. A kernel extension would not by itself protect against a compromised kernel or root administrator. A later hostile-host profile needs an independent authenticated enforcing controller/domain with suitable observation provenance; do not sell it as an automatic benefit of eBPF.

Lifecycle ownership is singular: service supervision owns the gateway process lifetime but cannot grant motion; the host helper owns sandbox start/cleanup; `actryn-robotd` owns skill preparation/state and persistence; the kernel owns effective grants and host dispatch; the controller owns its command-deadline response; the operator owns rearm and trusted-stack promotion. Deployment tools may install but cannot activate. Framework self-healing, ROS spawners, teleoperators, homing/reset routines and vendor interfaces must either submit through the same protected path or remain outside supported integration. Start framework hardware inactive, disable automatic authority restoration, and use one selected local scheduler. A second process watchdog is only application-health evidence, not whole-host protection.

## 4. A small kernel authority component, not a new operating system

Use a supported distribution kernel, systemd and cgroup v2. Start with a single qualified distribution family and exact server/robot kernel configurations; different board kernels are acceptable. First package targets are Linux x86-64 server and AArch64 robot, subject to target preflight. Kernel/configuration version strings are filled by qualification, not invented in this design.

| Concern | Initial mechanism | Boundary / failure rule |
|---|---|---|
| Files, credentials, processes, devices | Namespaces, mount allowlist, UID separation, dropped capabilities, seccomp, device policy | Verify the installed policy before starting untrusted code; deny raw controller, GPIO, bus, runtime socket and inherited handles |
| CPU, memory, I/O, task counts | cgroup v2 profiles; bounded application queues | Constrains consumption; does not prove robot deadlines |
| Server network access | No external agent network; dedicated namespace and scoped local broker channel | Broker owns allowed model/tool egress and credentials; target/site network policy separately closes routes from other hosts |
| Attribution | Trusted launcher records attempt before execution; cgroup/process lifecycle tracking | Never trust an agent-provided PID, cgroup or trace ID as authority |
| Required host denial | Existing kernel mechanisms; selected supported BPF LSM hooks only where needed | Attach/verification failure prevents that policy-dependent workload from starting |
| Diagnostic visibility | Counters/pressure first, then a small libbpf CO-RE probe set | Missing probes or dropped records mark coverage incomplete; no silent prevention claim |
| Typed motion limits, ownership, stale requests | Custom `actryn_authority` driver at its supported endpoint dispatch boundary | Generic BPF hooks do not supply these semantics; no coverage claim for unrelated drivers |
| Host freeze / loss of power | Named controller/protective mechanism | Cannot depend on another process on the same frozen Linux host |

The kernel's [cgroup documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html), [BPF LSM documentation](https://docs.kernel.org/bpf/prog_lsm.html) and [libbpf overview](https://docs.kernel.org/bpf/libbpf/libbpf_overview.html) support the separation between resource/access mechanisms and observation. CO-RE reduces dependence on kernel structure layouts; it does not guarantee available hooks or semantic compatibility.

Ship `bpf/` objects and a feature manifest as ordinary product artifacts. Fixed reviewed C BPF programs with a libbpf-based Rust userspace loader are the initial observation direction. Required denial links/policies outlive the diagnostic reader through protected ownership/pinning. Loss of required enforcement blocks new launches and applies the declared quarantine/termination policy to affected attempts; it cannot undo an earlier effect. Reader loss marks evidence incomplete and never relaxes denial. Each product profile identifies its required enforcement and denied-operation reporting sources and versions.

### Kernel responsibilities and UAPI

The first driver provides a **fixed typed command class for one wheel-pair/fixture endpoint**, not a universal robotics syscall. It owns endpoint state, immutable owner-policy ceilings, active instance/grant generation, robot-local expiry, the bounded queue, final validation, revocation, controller session/barrier state and the authoritative event sequence. Only controller facts parsed by its backend can complete handoff. It must not accept a userspace `safe=true` assertion as that fact.

Use a small character-device UAPI with separate administrator, runtime, acquisition and read-only event rights. Operations cover capability discovery, inhibited configuration, owner/instance registration, pending grants, prepare/activate, parent-operation/sample submission, operation cancel and trusted skill finish, grant revoke, query, context-revision invalidation and rearm. Exact struct layout is versioned under `kernel/include/uapi/` in the monorepo; the [kernel contract](../../architecture/kernel-controller-contract.md) fixes semantics first. Durable request-key lookup/tombstones stay in the robot manager; allocated operations close through this same kernel boundary. Operator configuration/rearm require the separate admin role; runtime requests cannot widen ceilings or clear stop latches. A passed FD does not transfer session ownership. Remote identity is authenticated by the trusted robot manager, not discovered by the kernel from a claimed model hash.

The admin role creates the pending grant under its installed policy. Runtime `ACTIVATE` and `SUBMIT` only consume that operator-authorized grant; they cannot mint or enlarge authority, even below global ceilings. The grant binds the permitted principal/instance, group, operation class, duration and limits. Normal replacement needs an authorized candidate grant in addition to a successful handoff.

Use fixed-width fields, explicit lengths/versions, initialized padding, checked arithmetic and bounded copies; no userspace pointers survive a call, no borrowed userspace memory drives output, and no kernel pointers escape in events. Unknown mandatory operations/features fail. Register the initial thread-group leader's kernel lifetime identity, retaining references rather than a numeric PID alone. Recheck it before dispatch and on the periodic owner check; leader exit conservatively ends the session even if other threads retain descriptors. Fork/FD transfer does not transfer ownership. Death detection is not instantaneous: finite local/controller deadlines cover delayed detection or a stalled daemon. The selected kernel's reference/exit/exec checks and export availability must pass the build/lifetime gate. Module reload and reconnect require a new runtime and wire session; no last-FD-close-only lifetime rule is allowed.

### First enforceable transport

The engineering candidate is a **dedicated UART bound through Linux serdev to a custom fixture backend**. Production endpoint selection follows the two-candidate comparison in §7. This is not confirmation of available Pi pins, wiring or deployed firmware. Successful binding must exclude a normal writable TTY; the target also disables competing console/debug/boot-time use and audits pinmux, raw MMIO, debug/flashing and alternate controller routes. A binding failure keeps motion inhibited even if Linux exposes a fallback TTY. USB serial requires a separately designed backend.

All first-profile output writes originate in that backend. The enforceable boundary is **acceptance into the underlying UART driver's buffer**, not the final physical bit. Serialize each nonblocking accepted prefix and effective revocation with one authority lock. The chosen recovery rule permits finishing only the one already-started immutable old frame, under a bounded recovery deadline, before the inhibit/barrier. Drop all wholly unsent old frames. Its fixed original deadline and residual effect remain visible; it receives no refreshed authority. If completion/barrier fails, latch the fault and rely on controller expiry. Already buffered bytes cannot be retracted. Flush/drain alone never proves handoff.

**New fixture wire contract, not existing Shrike compatibility:** every effect-bearing fixture frame carries controller boot identity, fresh negotiated session, grant/operation/sample identity and an absolute controller deadline derived conservatively from the clock mapping. Delayed receipt cannot restart a TTL. The session/reboot, sequence exhaustion, controller parsing and barrier rules are fixed in the kernel/controller contract. Existing Shrike framing/state machines supply lessons and regression cases; their current motor frames and quiet-period assumptions do not implement this v2 protocol. A legacy fixture handshake fails preflight. Native protocols are separate qualified backends under §7, never a fallback selected after handshake failure.

Use Rust for userspace and a portable `actryn-core` reducer. **Shared Rust semantics with thin Rust kernel glue are the first implementation candidate**, conditional on the exact supported kernel's abstractions, exports, toolchain, synchronization and lifetime feasibility (§7). If that gate fails, select a narrow C kernel implementation with recorded reasons and the same contract fixtures; do not require two production implementations. The inspected development tree is not the release kernel. Kernel integration may use a small justified C shim, but no custom JIT/verifier or programmable hook is needed for V1.

The reducer has bounded state and no I/O. Its hot path must allocate nothing and handle malformed inputs, overflow and capacity exhaustion explicitly. `no_std` alone does not establish those properties: for example, the existing AxiomOS `kernel_time` queue allocates at construction. Extraction must inventory and adapt actual dependencies, allocation and panic paths, preserving error handling and tests. Do not claim an unchanged, universally allocation-free core. Reusing production code in a userspace baseline reduces drift but is not an independent correctness oracle; retain independently specified transitions, golden frames, negative traces and Linux race/lifetime tests.

One authority lock orders all eligibility/publication and byte-acceptance mutations. A bounded worker executes ordinary queued transitions. An authorized cancel/revoke closes eligibility directly under that lock, outside the ordinary FIFO, before reporting local effectiveness; it wakes the worker for downstream recovery. Callbacks only capture bounded input/schedule work. Absolute deadlines are checked at the actual transition, so a captured-but-late receipt cannot win after timeout. No filesystem/network/model work or blocking controller wait occurs under the lock. The kernel contract specifies lock order, detached refcounted lifetime, callback/work cancellation and runtime-PM rules; exact implementation/build/race tests remain mandatory. Independent controller expiry covers host progress loss. The [source review](../../research/2026-10-13-source-review.md) records inspected API limits.

### What does not enter the kernel

Python, LLM inference, perception, motion planning, arbitrary policy graphs, artifact downloads/signature parsing and database writes stay in userspace. The kernel trusts its authorized manager's registration of executable provenance; this is weaker than verifying and executing the behavior bytecode itself in AxiomOS. It still independently enforces the installed command envelope, generations and endpoint protocol. The first release makes no claim that it runs AxiomOS managed programs or preserves their resource accounting.

No new JIT, scheduler, universal protocol parser or custom BPF verifier is selected. V1 fixed predicates cover numeric/identity/freshness limits. Replaceable admission predicates are a later bounded extension with a separately specified hook/context and verifier; they cannot widen fixed ceilings, alter owner transitions or clear latches. The custom driver is meaningful even without programmable predicates.

Measure the kernel component against the competent userspace baseline on the same endpoint. Its proposed benefit is enforceable single ownership at the supported host transport and a kernel-resident lifecycle when a userspace client misbehaves or exits. Kernel placement alone does not prove improved latency, resistance to kernel compromise, or physical safety.

## 5. The independent server product

Choose one initial sandbox backend: **OCI containers through containerd**, mediated by the restricted launcher. Reuse the runtime, not its unrestricted management API. A microVM backend is a later decision for a stronger stated threat model; Wasm is a different workload class. Wendy must not create a second independent sandbox lifecycle if its deployment integration is adopted.

The launcher creates `tenant → job → attempt → sandbox` records, allocates the cgroup and policy, prepares the workload without running application code, registers attribution and checks required enforcement, then releases execution. If the chosen runtime cannot provide that ordering, the launch integration fails acceptance. Fork/exec descendants inherit the attempt association; migration outside the designated cgroup is denied. Process identity includes host boot/lifetime information, not PID alone. Cgroup IDs and paths are also scoped to their lifetime. Cleanup includes descendants and credential revocation.

Start with process lifecycle, CPU/memory/pressure, I/O and network metadata. Correlate explicit model and tool spans through our client/broker. Add scheduling/page-fault probes only to answer a specific diagnosis question. Shared inference workers retain explicit request spans; a host cgroup cannot attribute every shared GPU operation to an individual request. A microVM appears as host VM activity unless an independently trusted guest collector supplies finer evidence.

Charge delegated broker work as well as the sandbox. The platform contract requires finite per-attempt/global reservations for queued and executing calls, bounded request/response buffers, deadlines and applicable provider budgets. A reservation follows work after dequeue and remains charged through uncancellable external execution or uncertain recovery. Attempt termination closes publication contexts immediately; it does not manufacture capacity by forgetting outstanding work. Reports separate sandbox usage from reserved/observed delegated consumption and unresolved external outcomes.

Expose a report such as: attempt X exceeded its memory budget; subprocess Y made a failed device-open request; the broker denied a named method under rule Q; inference request Z overlapped I/O pressure. Preserve unknowns, probe loss and clock uncertainty. Do not infer plaintext model activity from encrypted sockets or equate network events with completed tool effects.

The [platform contract](../../architecture/platform-release-contract.md) selects the launch order and a policy coverage table. Reports distinguish `policy_denied` from `access_failed` and `coverage_unavailable`: an `EACCES`/`EPERM` syscall result alone does not identify which policy caused it. The initial demonstrable attributed denial is the scoped broker's rejected method/resource request; stock OS failures retain the narrower label unless the selected enforcement source supplies a matching fact. ActPlane/Actime remain optional and must qualify the actual integration path; a language feature or post-event kill is not inherited pre-effect blocking.

Provider credentials belong to the scoped broker; the agent receives only its attempt-bound channel. Do not mount site credentials or expose robot administrator keys. Default evidence stores metadata, not full prompts, images or secret-bearing payloads. Content capture is an explicit site policy. Each attempt declares capture requirements and playback eligibility; the full observation/model-output demonstration requires that capture profile to be enabled (§8).

A server-only release exits when isolation, attribution, denied-operation reporting, resource-pressure diagnosis, cleanup and evidence export work without a robot. Implement and accept this lane alongside endpoint/kernel work; D2 requires its server profile inputs, not completion of robot D0/D1/D4. Keep containerd as the initial backend; a systemd-based alternative must demonstrate the same launch ordering and restrictions before replacing it. No new VMM is selected.

## 6. The robot execution contract

### Objects, identity and API

| Object | Meaning |
|---|---|
| Agent artifact | Immutable server OCI image/manifest digest; installation grants no authority |
| Skill artifact | Immutable configuration naming a release-built local skill, compatible profile, bounded arguments and versions; no V1 uploaded code |
| Instance | Fresh local skill state in `actryn-robotd`, bound to one authenticated server attempt and prepared artifact |
| Owner policy | Operator-installed immutable revision of the allowed envelope and recovery conditions |
| Grant | Robot-issued, principal/instance/group-scoped permission with local expiry and generation |
| Operation | Stable externally meaningful requested effect, with digest and durable identity |
| Proposal | Immutable parent request referencing grant, skill/context and observations; child samples have separate identities/digests |
| Observation record | Robot-retained provenance, acquisition/receipt times, calibration and validity |
| Outcome | Separate admission, delivery, reconciliation and physical-evidence facts |

Use a versioned Protocol Buffers RPC schema for management and proposal traffic over end-to-end authenticated TLS through the unprivileged gateway; the trusted manager terminates TLS and performs authorization. Local administrative access uses a separate protected Unix socket with peer identity checks and bypasses the gateway. The initial Python SDK and CLI are thin clients of the same API. Use an established RPC/crypto implementation, not a bespoke transport. Bulk images use a separate bounded channel/object reference; no high-rate image stream shares the dispatch queue. Controller serial/CAN framing remains endpoint-specific.

The robot binds the authenticated peer to its local principal and grant; a request's identity fields are not proof. A compromised server can act within its delegated bounds, so the robot's policy cannot depend on the server being honest about model intent. Device pairing, software deployment, grant issuance and rearm are separate scopes. A renewal cannot revive an expired/revoked grant or clear a stop latch. Loss/revocation of a paired credential must take effect locally according to a finite delegation lifetime even during disconnection.

Enrollment uses the protected local administrative socket and operator verification of the robot CSR/public-key fingerprint, followed by the site's offline issuance and local certificate/trust-root installation. No unauthenticated network enrollment is provided. The platform contract defines scopes, renewal, offline delegation expiry, compromised/lost-key recovery and decommissioning. Deployment credentials cannot issue grants. Re-enrollment/reconnect never rearms or revives an operation.

An initial proposal names schema version, stable attempt-scoped request key, immutable payload digest, instance, endpoint group, runtime/grant identity, approved skill parameters, context/observation IDs and requested horizon. The robot durably binds its operation ID before any effect and returns it; a lost response does not undo admission. Query/cancel accept either the returned ID or the authenticated attempt/request key. Read-only key lookup never creates or resends work. Cancellation of an unallocated key durably terminalizes it; cancellation of an allocated key uses urgent kernel closure. The platform contract serializes key cancellation with allocation/submission and defines durable, locally-closed and reconciled acknowledgements. The broker binds pre-allocation context to the request key and appends the robot ID when known; the agent never invents a kernel operation identity. Internal samples use the allocated ID. The V1 backend receives only the fixed `WheelDutyPair` class, not arbitrary modes. The robot supplies deadlines from its clocks/retained context. Reject unknown fields/features, nonfinite values, overflow, incompatible units/frames/revisions and excessive payload/queue sizes. Server wall-clock timestamps are diagnostic only.

The V1 wheel pair is one indivisible arbitration group with at most one live parent operation. Only one final host dispatcher commands it. Controller expiry/protection may disable output independently; no active balancing/holding authority is claimed. Future coupled or stabilized profiles require a distinct contract for bounded task targets feeding trusted stabilization, with protective authority independent of experiment grants; they cannot reuse this fixture qualification by renaming a command mode.

### Observation validity and timing

Sensor records distinguish acquisition from host receipt. For V4L2, inspect timestamp clock/source flags and the exact driver/capture path; a buffer timestamp is not automatically the required monotonic acquisition bound. If sensor time is not directly in the robot clock domain, retain a qualified clock mapping and its error bound. If acquisition age cannot be bounded, mark it unknown and deny operations requiring bounded acquisition age; a recent USB receipt does not repair an old buffered image. Calibration changes invalidate dependent observations.

A calibration or clock-map change occurs while inhibited in V1: close dependent operation eligibility under the authority lock, reconcile, install the new revision, discard old observations and explicitly rearm. Observation IDs are source-lifetime scoped, immutable and never recycled within that lifetime; missing/overwritten IDs fail. Reject future/inconsistent timestamps and excessive mapping uncertainty. V1 waits for each `SAMPLE_APPLIED` receipt before starting the next sample. Slew validation uses that last controller-applied output/time with bounded elapsed credit, and the controller independently enforces its actual applied-output ceiling. Unknown application cannot supply extra slew credit; it closes ordinary dispatch until reconciliation. Host accepted bytes remain a different evidence frontier.

The trusted acquisition bridge registers a small bounded context through a separately authorized kernel interface: source/observation ID, acquisition-time bound, clock/calibration revisions and typed state needed for the fixed gate. The kernel copies and validates that context, records its receipt time and checks required age/version at dispatch. It does not parse camera images or independently prove a sensor's timestamp. That bridge and its clock mapping remain trusted; an agent cannot register replacement observations or refresh an old record by reusing its ID. The large observation payload/cache stays in userspace.

Use a robot clock contract that accounts for suspend; the physical profile disables suspend and treats a detected discontinuity/resume as inhibition and reconciliation. Do not let a stopped monotonic clock extend authority across suspend. Observation cache misses, overwritten records, stale local state and invalid confidence fail the relevant precondition. Model-generated world descriptions remain estimates, not trusted sensor assertions.

Perception estimates retain input IDs, derivation/model version, measurement-support interval, visibility, calibration/frame/scale and uncertainty. An inference completion timestamp cannot refresh old or occluded measurements. Each reviewed skill declares the support and geometric/contact checks it requires, and the scenes it does not support. The fixed kernel gate reports only its numeric/identity/freshness predicates; admission is not general collision clearance. The first wheel fixture uses known restraint/exclusion geometry and measured output limits, not model-derived collision assurance.

The trusted server broker binds inference request, launcher attempt, observation digests, model/provider/checkpoint, prompt/context compiler, demonstrations and response to the proposed operation/subtask. The robot validates context identity/lifetime and its own retained observations. Treat this as server-attested provenance: a compromised server can fabricate its lineage, and no record proves a model attended to an image. Fresh local preconditions still control dispatch. Close contexts on operation closure, expiry, replacement and attempt termination; reset planner/progress/local skill state on activation. Reject late Corrector/progress results for a different operation and prohibit unversioned live model changes within an attempt.

Adapter schemas bind units, coordinate convention, quaternion/joint ordering, normalization revision and embodiment masks. Convert once at the reviewed userspace boundary; reject unsupported or missing dimensions, and never infer their semantics from a vector length. No UnifoLM/other research action vector is accepted as a universal motor command.

Separate five horizons: observation validity, agent computation, admitted skill duration, authorized dispatch horizon and downstream accepted work. Under the brief's illustrative 10–50 ms RTT, a round trip alone spans 5–50 periods at 500–1000 Hz. That calculation motivates local control; it is not a measured network profile or a promise that the robot daemon runs at those frequencies.

### One authoritative mutation order

The portable Rust `actryn-core` expresses deterministic authority/lifecycle transitions. Its selected production integration must establish Linux synchronization and lifetime guarantees independently. A userspace baseline can reuse the reducer but owns no live production authority. Compare transitions and event meanings against independently specified expected results; executing shared code twice is not an independent oracle. Where a C fallback is selected, differential tests additionally check cross-language consistency.

The authority lock is the single mutation order for effective grant, generation, publication, parent-operation eligibility and transmit queue. Admission and insertion are one transition. Ordinary work runs on the bounded worker; urgent cancellation/revocation closes eligibility under the same lock without waiting behind queued submissions. The return states are request accepted, locally effective, downstream reconciled and physically observed/unconfirmed. At every UART accepted prefix, recheck live identity, absolute deadlines and context, except the explicitly identified completion of the one old partial frame. There is no independent adapter writer.

Never hold the authority lock waiting for network, fsync, model inference or controller acknowledgement. Completion callbacks carry full operation/session/generation/transaction identity and cannot mutate a terminated transaction. Required shutdown/protection state and wakeups use preallocated storage; no full submission queue can prevent eligibility closure. The worker checks urgent closure/expiry before ordinary work and limits each turn; this is an ordering rule, not a hard scheduling deadline on unqualified Linux.

An output stream is not transactional. Track `UNSENT`, `TRANSMISSION_STARTED`, `LOCALLY_WRITTEN` and the endpoint's actual acceptance/reconciliation facts. Cancel wholly unsent frames; finish only the already-started immutable frame before the barrier under the selected recovery bound. Never label local closure as zero residual motion. A local write completion proves neither controller acceptance nor physical response.

### Lifecycle

```mermaid
stateDiagram-v2
    [*] --> INHIBITED
    INHIBITED --> READY: reconcile + explicit authorized rearm
    READY --> ACTIVE: activate prepared instance and new grant
    ACTIVE --> REVOKING: normal grant revoke / takeover / replacement
    REVOKING --> READY: normal revoke/replacement, reconciliation established
    REVOKING --> FAULT_LATCHED: timeout / expiry / owner loss / reset / unknown
    ACTIVE --> FAULT_LATCHED: expiry / owner loss / reset / protective fault
    FAULT_LATCHED --> INHIBITED: authorized recovery and reconciliation
```

This is the endpoint grant/session lifecycle. Parent-operation cancel and trusted `operation.finish` are separate: both close that operation/stream through the existing urgent path while retaining an otherwise live grant. Finish records `SKILL_FINISHED`, not verified task success. No next operation may dispatch until the matched quiesce barrier establishes the disabled-zero baseline and reconciles. The first matching normal close fixes its reason; a later cancel/finish cannot relabel it. Grant revocation or a fault may escalate closure, and expiry/owner loss/reset still dominate a late success. A failed handoff latches the endpoint. Physical target success can coexist with failed reconciliation.

Candidate preparation is also orthogonal: reserve bounded capacity, then prepare B without active authority while A operates. The platform contract charges the simultaneous active, staged and retiring state and bounds preparation work; deterministic rejection preserves A. A daemon crash or OOM instead invokes owner-loss protection, not an unaffected-A claim. Publication consumes the candidate's existing reservation with the expected-generation check; abandonment/failure/restart must settle resources. Replacement closes A, reconciles, then publishes B with a separately preauthorized grant, fresh state and new generation. Authorized recovery and explicit rearm are required after faults; a delayed receipt never clears a latch or publishes a timed-out candidate.

V1 state policy is **fresh state on activation**, including selecting a previously used artifact. No arbitrary state migration, transparent CRIU restoration or physical rollback. Restoring a process cannot restore a robot session or grant. Robot daemon restart creates a fresh runtime epoch even within the same OS boot; controller restart changes the endpoint session and inhibits its group. Neither automatically resumes motion.

Operation IDs are allocated by the robot under a kernel-issued nonrepeating runtime epoch. The client supplies a stable proposal request key within its attempt; the robot durably binds that key, operation identity and payload digest before first possible dispatch. Same ID/same digest returns the known state; same ID/different digest is rejected. After restart, **every unfinished durable operation is conservatively `OUTCOME_UNKNOWN`**, even when it might never have dispatched, until reconciliation establishes more. Never automatically resend it. Known old IDs remain queryable; retired epochs cannot create new effects, even after result compaction. The SDK never changes epoch or request key to turn a retry into a fresh action. This is not an exactly-once physical-effect guarantee.

The SDK exposes the stable request handle before sending the first proposal, so a timed-out caller can query or cancel without resubmitting. Key records/tombstones are bounded and retained while their attempt/epoch can still admit work; capacity exhaustion rejects new admission rather than evicting live cancellation history. Key cancellation closes the server publication context, but only robot acknowledgements establish robot-side effectiveness. Storage failure cannot delay urgent closure of an allocated operation, and cannot justify a durable-cancellation claim. Retired request namespaces never regain admission during recovery.

Persist the immutable parent intent in preparation, then submit it and recheck all live conditions. Child samples carry `(operation, stream, sequence, digest, context, deadline)`; retained exact duplicates return the original status without deadline refresh and changed-payload duplicates reject. Older samples outside the bounded result slot reject as retired. Operation cancel closes that child stream under the authority lock even if the grant remains valid. A completed/cancelled parent cannot accept late samples or resume under a new epoch; sequence exhaustion closes the stream instead of wrapping.

V1 has one started frame and one replaceable latest-value sample, with no next sample transmitted until the current controller receipt. Higher sequences replace only the unsent mailbox. Arbitrary trajectories/action chunks are rejected. This throughput choice fits the restrained fixture and makes no 500–1000 Hz dispatch promise. A future chunk extension must define local target steps/times, execution period, predicted/authorized/committed/applied frontiers and elapsed-sample rejection; it may replace only wholly unsent work and must condition on actual clamps/interventions/acceptance. RTC is a compatible-policy implementation option after that extension is qualified. Sample silence reaches the fixed endpoint deadline and disables output. Samples are asynchronously recorded, not individually fsynced, so their crash-lost tail remains explicitly possible.

## 7. Endpoint support is a qualified contract

Select the first physical endpoint by its enforceable route and recoverability, not its popularity. A Shrike-derived restrained motor fixture is the first engineering candidate because source exists; exact board, electrical response, motor/driver, instruments and firmware remain unselected. No physical result is claimed.

| Concrete candidate | Evidence-backed fit | Required adaptation / unresolved cost |
|---|---|---|
| Shrike/RP2040 restrained wheel-pair fixture over dedicated host UART | Local codec, handoff and firmware source/regressions are inspectable; dedicated UART matches the proposed serdev exclusion path | New v2 protocol, persistent boot identity, deadline clock mapping and actual output-disable chain; selected board/pins/motor/driver/FPGA role and electrical qualification remain open |

The first remains the engineering preference, not an approved physical product. D0 records route coverage, native semantic conformance, necessary firmware/backend changes, recovery observability, installation effort and customer workflow fit for both, then selects exactly one. Missing source/build/hardware results are recorded `NOT_RUN`, not scored as a benefit. If neither meets the contract, physical activation remains blocked; do not weaken the contract to finish a demo.

Separate required endpoint semantics from fixture encoding. Each native candidate maps its actual commands/receipts to typed values, nonreused identity and retirement, finite non-renewable effect horizons, queue/partial-transmission behavior, applied-output evidence, quiescence, reboot inhibition and independent host-loss response. The same conformance traces and exclusive kernel route must hold; parsed/queued acknowledgement cannot become `SAMPLE_APPLIED`, and a receive-relative watchdog is not an absolute effect bound. Preserve stable external operation identity even if the native wire uses another representation. A duty command cannot be silently translated into a velocity mode; incompatible command semantics need a separately reviewed typed profile. An unmapped obligation rejects the candidate. Keep fixture v2 for the custom fixture; choose native adaptation, firmware modification or rejection based on demonstrated gaps, never automatic fallback.

Use the **small kernel gate plus trusted userspace skill/persistence** split. A fuller in-kernel behavior/program runtime adds verifier/scheduler/allocator obligations without a V1 execution-class need, so it is deferred. For the selected target kernel, first build the minimal shared-Rust reducer/glue path and check required abstractions, exports, synchronization, lifetime and maintenance cost. Compare a minimal C fallback only where that path has a concrete support gap or disproportionate patch cost. Freeze one implementation with the same conformance cases; available Rust source alone does not pass the gate. The development Linux checkout establishes neither result. This is a build/support gate, not an invitation to add another runtime.

Every target package must declare:

1. Exact hardware, controller firmware, host/kernel configuration, cooling/power, payload/calibration and independent protective mechanism.
2. All actuation routes: device nodes, sockets, network services, raw buses, shared memory, inherited descriptors, debug/flashing interfaces and controller-local autonomous modes.
3. Final reject/dispatch point, all trusted code after it, every downstream queue and its bound.
4. Supported typed commands and intentionally unsupported modes, limits, units, frames, coupling and timing inputs.
5. Cancellation, barrier, acknowledgement and expiry meanings; whether a receipt proves parsing, queue removal, controller state, or something physically measured.
6. Agent-loss, daemon-loss, host-loss and controller-restart behavior, including distinct braking, holding, torque-disable and power-removal semantics.
7. Recovery/rearm preconditions and the independent observation needed to claim takeover complete.
8. Exact tests and required measured limits for this version; omitted critical limits make a physical profile invalid.

A controller watchdog refreshed by any arriving byte may be kept alive by obsolete queued traffic. The fixture therefore uses the new session-bound absolute controller expiry contract, including a bounded host/controller clock mapping and original deadlines on partial-frame completion. A native endpoint must independently establish the same required finite effect bound and stale-work rejection; a receive-started TTL alone is not an allowed substitution. The selected protocol's reboot-identity, parsing and complete disable mechanism must be tested. Existing Shrike firmware is an extraction input, not an implementation of these requirements. Evaluate independent FPGA versus simpler watchdog protection against the named fault model before selecting hardware. The retained small FPGA gate consumes `command_valid`; its watchdog lives in the top-level logic and depends on the actual clock. Rewriting that logic requires renewed qualification. A watchdog that detects command silence does not by itself detect continued erroneous commands from a faulty MCU.

For ROS 2, leaving `/cmd_vel`, controller-manager switching, a vendor service or direct bus access reachable can bypass the product. Protect the entire actual path, including commands from other hosts. A ROS adapter is supported only when those routes and downstream queues are closed or explicitly trusted. ROS graph membership and successful message delivery are not authority.

The reviewed local skill may continue through ordinary agent disconnect only within its fixed operation/grant/context deadlines and installed continuation policy. Supervised gateway exit/replacement or required authenticated-session liveness loss instead closes affected contexts and revokes their grants as specified in the platform contract; neither reconnect nor gateway restart restores authority. Controller expiry independently requests zero/disable; this profile has no powered-hold or balancing obligation. Homing, opening a gripper, AutoReturn, braking, holding, torque disable and power removal are distinct physical actions, not generic synonyms for safe recovery. Future endpoints must install their exact protective authority. Human takeover uses the same ownership/handoff rules; a CLI stop is never represented as a physical emergency stop.

## 8. Evidence, persistence and inspection

Use **SQLite** for local operational metadata/intent/result indexing and **MCAP** for timestamped event/sensor recordings. Keep them on bounded separate write paths from dispatch. A recording format supplies records and indexes, not proof of physical completion; see the [MCAP specification](https://mcap.dev/spec). Export OpenTelemetry spans for application/host correlation and integrate a viewer such as Rerun only through a read-only exporter.

Each authoritative event contains producer identity and lifetime, monotonically increasing producer sequence, local time/clock domain, contract/configuration identities, attempt/operation/observation references, and its precise evidence class. Correlation IDs connect records; the originating trusted component supplies each fact. Agents may append their explanations, but cannot overwrite admission, controller or measured outcomes.

Kernel admission/publication/dispatch events are read from a bounded stream and persisted by the trusted recorder. Sequence loss and producer/session changes remain visible; manager events cannot replace missing kernel facts. Track per-producer read, queued-for-persistence and durable frontiers separately. The writer persists required recording files before committing their checkpoint to SQLite. Recovery preserves raw remnants for diagnosis but excludes unsupported tails/checkpoints from authoritative results. Reader acknowledgements do not advance durability. The kernel receives bounded trusted writer-health/progress assertions, not filesystem I/O or a new evidence database.

Keep admission (`allowed`, `clamped`, `rejected`), delivery (unsent/partial/controller accepted), lifecycle (revoked/reconciled/unknown) and physical evidence (observed/unconfirmed) as separate dimensions. A clamp reports requested and admitted values. A controller receipt can coexist with `physically_unconfirmed`. Learned progress/success/failure attribution includes model/version, operation/subtask epoch, distribution or uncertainty, and unknown/multiple-cause labels; it cannot overwrite observed faults. Dataset export preserves clamps, interventions, stale rejections and gaps before assigning any training label. A cancelled or censored attempt is not automatically a planner failure or task success.

Critical parent-operation intents become durable before dispatch. Continuous sample records persist asynchronously. Required finite profile inputs are volatile bytes/record capacity, maximum pending-record age since durable progress, health interval and closure/recovery bounds. Crossing either age/capacity bound closes new admission **and urgently revokes existing experimental streams**; no healthy read cursor permits continuation. Stop/protection never waits for recording. Reserve essential transition capacity but still expose exhaustion. A crash can lose the last gap record; unfinished intents, producer changes and durable frontiers also mark uncertainty. No zero-loss or arbitrary media-failure guarantee is made.

Every attempt has a capture manifest: requested/retained streams, payload-versus-metadata policy, producer/trust/clock identities, model/context/configuration digests, sequence ranges/gaps, retention/redaction, durable frontiers and separate event-playback/execution-replay eligibility. Metadata-only capture supports diagnosis, not full input replay. A missing payload hash cannot replace the payload. V1 execution replay requires a known fresh activation boundary and the complete ordered input prefix, including clamps/interventions/controller results, to reconstruct skill state before any requested interval. If that prefix is missing, permit timeline playback with explicit state-unknown/gap labels, not execution replay from invented fresh mid-skill state. Replay-only state checkpoints are deferred. Replay uses a simulator identity with no live keys, devices or command-service path. Fresh inference reproduction is a separate experiment; complete capture does not authenticate a compromised server's records or make model outputs deterministic. An agent-controlled `--replay` flag is not the isolation boundary.

Initial UI: CLI plus a generated attempt report/timeline and an existing viewer. Build a cockpit only after operators repeatedly need a workflow those surfaces cannot support. Do not build a trace database, plotting system and fleet dashboard in V1.

## 9. CLI, SDK and distribution

One `actryn` command, task-oriented nouns, structured `--json` output, stable reason codes and actionable operator messages. A guided `actryn workflow --robot <robot> --attempt <prepared-attempt>` view presents the existing stages and resumes by querying their stable identities. It shows authenticated principal, target/profile, requested limits and current generations. Each grant, activation or rearm remains a separately authorized explicit action; pairing or pressing resume cannot mint authority, replay effects or automatically rearm. Scripts use the same underlying commands and acknowledgements. The guide adds no alternate execution engine. The following illustrates the proposed surface; these commands do not exist yet:

```text
actryn doctor --role server
actryn doctor --role robot --target <target-package>
actryn device enroll request                 # protected local robot console
actryn device enroll install <signed-cert> --trust-root <site-root>
actryn device pair <robot> --fingerprint <verified-fingerprint>
actryn robot describe <robot>
actryn bundle inspect <bundle>
actryn bundle install <skill-config> --robot <robot>
actryn attempt prepare <agent-image-digest> --profile server-restricted
actryn instance prepare <skill-config> --robot <robot> --attempt <prepared-attempt>
actryn grant issue --robot <robot> --instance <id> --attempt <prepared-attempt> --policy <policy>
actryn robot rearm <robot> --expected-generation <generation>
actryn instance activate <id> --expected-generation <generation>
actryn attempt start <prepared-attempt> --grant <grant>
actryn operation inspect --attempt <attempt-id> --request-key <key>
actryn operation cancel --attempt <attempt-id> --request-key <key>
actryn operation inspect <operation-id>
actryn operation cancel <operation-id>
actryn robot reconcile <robot>
actryn attempt inspect <attempt-id>
actryn evidence export <attempt-id> --output <directory>
actryn replay <recording> --target simulator
```

`attempt prepare` reserves launcher-owned identity, finite preparation capacity and the verified stopped sandbox before a grant can bind it; it does not run the agent. Prepared objects have bounded lifetimes and consume capacity until actual cleanup. `instance prepare` reserves staged robot capacity before constructing state. `grant issue` creates only a pending bounded grant for that principal/attempt/prepared instance; eligible activation makes it effective. `attempt start` rechecks prepared policy/identity and consumes the intended binding; failure leaves no new effect and the finite grant can be revoked. Server-only attempts use prepare/start without a robot grant. `rearm` is an authorized operator operation after local recovery checks, not behavior activation. Grant issuance, rearm and activation are unavailable to ordinary agents. Key-based `inspect` is read-only. `cancel` reports pending/durable-key/locally-closed/reconciled facts separately, with nonapplicable stages explicit; timeout is not success. An unallocated cancelled key needs no controller barrier, while allocated work must follow its actual handoff. Outputs include authoritative generations and transition IDs. Local recovery remains available without the server.

The Python API initially needs describe, observe, propose, query and cancel, with typed inputs and structured outcomes. A stable request handle is available before proposal transmission; query/cancel accept that handle even without an operation ID. A client timeout never creates a new key or reports cancellation as effective without the relevant acknowledgement. Natural skill finish is internal to the trusted executor, not a tool allowing the agent to assert physical completion. The SDK does not mirror the entire administrator API or expose raw register writes. RAI or another agent framework integrates as a client of this API only after a concrete application warrants it.

# V1 kernel and controller contract

Status: selected design, 2026-10-13; **not implemented or qualified**. This specifies mechanisms for findings 1–6 and 8 of the [independent attack](../reviews/2026-10-13-architecture-attack.md) and the subsequent [brief cross-reference](../reviews/2026-10-13-post-patch-brief-review.md). It is the normative kernel/controller companion to the revised main architecture. Target API, firmware and physical validation remain required.

## Scope and authority

V1 supports one restrained wheel-pair fixture requiring neither active balance nor powered load holding. Its protective response requests zero drive and output disable; electrical disable and resulting coast must be qualified. No braking-distance, humanoid stabilization or active-hold claim follows. A trusted local skill converts bounded task targets to typed wheel commands; it has no raw transport. Its lifetime is separate from the remote agent's, but its command authority remains bounded by its operation/grant. It may continue an already admitted skill only to that operation's fixed deadline. Controller-side expiry remains independent of Linux and never depends on model or recorder progress.

The mandatory custom kernel component owns one copied typed command, fixed limits, effective grant, generation, operation lifecycle and exclusive endpoint dispatch. Its V1 command is `WheelDutyPair`: signed integer left/right drive duty in permille, representable range [-1000, 1000], with no unit/mode switching. Installed target ceilings may be much smaller; representability is not physical permission. Wiring polarity, channel order, numeric/slew ceilings and zero/disable behavior are immutable qualified profile data. Userspace owns artifact execution, inference, durable intent and recording. Dedicated serdev UART with a shared portable Rust reducer and thin target-supported kernel glue is the first engineering candidate. The main architecture's exact-target build/lifetime/export gate may select a documented narrow C fallback; only one production implementation is required. ## One serialization order, urgent closure

One per-endpoint authority mutex serializes effective state changes and every `serdev_device_write_buf()` call. A bounded worker processes ordinary admission/RX/transmit events. **Urgent close ioctls acquire the same mutex directly**, rather than waiting behind its FIFO. Thus the worker is not the exclusive mutator; the mutex defines the sole mutation order. No second userspace ownership table is authoritative.

The worker checks pending closure, expiry, owner liveness and evidence health before ordinary work, handles at most one bounded event/frame-prefix write per lock acquisition, then releases the mutex. Validated closure publishes expected lifetime/generation/transition identities into fixed control slots for endpoint fault/detach, grant revoke and operation close before waiting for the mutex. Under a bounded IRQ-safe control lock, requests merge monotonically: detach/fault dominates grant revoke, which dominates operation close. A weaker request cannot erase a stronger one; a stale request cannot overwrite a current identity. Overflow of a required closure slot escalates to endpoint fault rather than dropping closure. Timers/callbacks use these slots and schedule work without acquiring the authority mutex.

The registered trusted runtime's internal `operation.finish` requests this same urgent operation-close path with reason `SKILL_FINISHED`; ordinary cancellation uses `CANCELLED`. The first matching operation-close request recorded under the control lock fixes its normal reason; later finish/cancel requests are idempotent and cannot relabel it or create a second barrier. Grant revoke, expiry and fault still dominate eligibility and the resulting lifecycle outcome; retain the initial reason only as history. A skill return or target-reached observation alone never releases the group. Task success and close reason remain separate evidence fields.

Pending closure is notification, not a second effective grant table. Ordinary writes stop while it is pending. Under the authority mutex, revalidate slot identities and commit effective closure; clear only the exact slot revision processed, leaving concurrently published requests pending. Never hold the control lock while acquiring the authority mutex or calling the UART; callbacks never acquire the authority mutex. Interrupted callers do not withdraw an accepted closure. RX queues cannot consume control-slot storage. This prevents cancel/revoke/teardown races from downgrading closure without inventing a scheduling guarantee.

| Event / receipt | Meaning and ordering |
|---|---|
| `CLOSE_REQUESTED` | RPC/event accepted; authority might still be effective. An interrupted syscall returns no stronger claim. Query by transition ID. |
| `LOCALLY_CLOSED` | Under the mutex, mark grant/operation ineligible, advance the applicable generation, close child streams and discard unsent work. This is the linearization point. |
| `RECONCILED` | Matching controller barrier received and processed before the transition's absolute deadline; establishes only the declared controller state. |
| `FAULT_LATCHED` | Timeout, owner loss or protective fault closes eligibility; a delayed receipt cannot undo it. |

After local closure, no new experiment frame may enter the UART buffer. Only the exact started-frame recovery allowance below and protective protocol frames remain eligible. Each such write checks detached state, recovery/session identity and deadline. The mutex may be held across one asynchronous buffer-write call, never a drain, synchronous write, controller wait, allocation, filesystem or network operation. Actual UART-driver call duration and callback reentrancy must pass target inspection; “asynchronous” alone gives no scheduling bound. No callback may reacquire the authority mutex from that call. Event capture uses a separate bounded queue lock; the worker releases it before taking the authority mutex.

Expiry is checked using current robot boot-time clock at every transition, including processing receipts captured earlier. Deadline/closure wins over completion at equality. Owner-death detection is not instantaneous; local closure latency, retained UART bytes and physical response are separate measurements. If Linux cannot run the closure path, controller expiry is the remaining response.

## New fixture wire protocol

The proposed **Actryn fixture wire v2 is incompatible with existing Shrike v1**. Existing codec/state-machine tests are extraction material, not implementation of this contract. There is no automatic v1 fallback or live protocol negotiation.

The dedicated physical link is trusted against hostile injection; CRC detects corruption, not authentication. Use bounded delimiter framing, fixed permitted message lengths, CRC, explicit version, and finite parser storage/timeouts. An invalid frame cannot refresh liveness. Every command, start/rearm, quiesce, fault, receipt and other state-changing message carries:

`device_identity, controller_boot, controller_session, host_runtime_nonce, grant_generation, operation_id, stream_id, sequence, transaction_id` as applicable. Unused fields have canonical zero values, not wildcard meanings. Commands additionally carry typed values and an **absolute controller-clock expiry**. Receipts echo the identities and controller state/time they actually establish.

The controller durably increments a nonwrapping boot counter before accepting handshakes; failed/ambiguous persistence inhibits output. It creates a fresh nonwrapping session counter/challenge for each handshake while inhibited. The host supplies a fresh 128-bit runtime nonce from initialized kernel randomness and accepts only the matching response. Rearm consumes that challenge once. Replayed handshakes cannot reuse an old session. Counter exhaustion inhibits and requires servicing; firmware reinstall cannot silently reset the device identity/counter namespace. Commissioning a replacement identity requires explicit operator recovery. This is a selected firmware requirement, not a verified property of a Shrike/RP2040 board.

Any controller reset starts with outputs inhibited and previous sessions invalid. The host closes authority on a changed boot/session or lost link; it cannot infer absence of a reset merely from missing telemetry. Old commands retained in UART buffers are rejected by identity after reset and by expiry without a reset. Host/module restart likewise creates a new session and cannot adopt the old operation. Within a session, grant generations never decrease and operation numbers strictly increase. `START` advances the operation high-watermark but never actuates; quiesce also retires an operation that has not started. A command cannot reopen a retired operation, and a sample cannot mint a grant or operation.

The kernel-issued operation epoch includes device identity, controller boot/session and host runtime nonce; live operation IDs cannot be allocated until that handshake completes. Durable boot plus per-boot session counters prevent reuse of the full wire epoch; the nonce is not the sole uniqueness argument. Offline software fixtures use a separate non-actuating identity namespace.

The handshake establishes a bounded mapping between host boot-time and controller monotonic ticks, including measured exchange uncertainty and specified oscillator drift. Host cutoff `H` is the minimum of grant, parent operation, required observation-validity cutoff and the sample's finite dispatch horizon; credential/health ceilings constrain grant/operation as applicable. Choose controller expiry no later than the conservative lower bound on controller ticks at `H`. Invalid/too-uncertain mapping inhibits; recalibration is performed inhibited. Controller expiry is checked before applying each command and throughout execution. Neither delayed receipt nor acknowledgement renews it. An operation has a controller-enforced absolute end time; sample deadlines cannot exceed it. No remote wall clock is authoritative.

### Selected partial-frame rule: finish one old frame, then quiesce

There is at most one started command frame, one replaceable unsent sample, and no transmission of a subsequent sample until the current sample's controller receipt. This deliberately limits V1 throughput; it is not a servo-rate promise.

On close, drop the unsent sample. If a frame has started, finish **only its exact immutable remaining bytes**, with its original identities/expiry, within the profile's recovery deadline. Do not append new command content, increase its horizon or refresh its grant. That old frame may still cause a residual effect before its original expiry. Then send a uniquely identified quiesce barrier, without waiting for the old command receipt. If completion stalls or errors, stop sending, latch a fault and rely on independent endpoint expiry; do not splice stop bytes into the partial frame.

The controller processes complete frames in order, closes the named operation/session on quiesce, removes pending task work, requests zero/disable, then acknowledges the resulting controller state. Unknown sink/disable status produces no successful reconciliation receipt. Normal quiescence does not set the protective fault latch. Timeout, reset, host loss and protective intervention do; these require explicit operator rearm. Reopening after a transport fault requires inhibited parser/transport recovery and a fresh handshake. A flush alone is insufficient.

A successful sample receipt is `SAMPLE_APPLIED`: emitted only after the controller sink/command-register update succeeds, echoing the actual applied duty pair and controller application time. Parsed/queued receipt is insufficient. Unknown application status faults instead of supplying a slew baseline. Initial rearm and matched quiesce establish an explicit disabled-zero baseline/time before the first new sample. These are controller-reported command/output-state facts; they do not measure wheel motion or prove electrical disable independently. Host/kernel evidence must retain that distinction.

| Transition | Following state |
|---|---|
| Natural skill finish + matched quiesce | Operation terminal with `SKILL_FINISHED` reason; release the group only after timely reconciliation. A distinct operation may use the still-valid grant without rearm. |
| Normal operation cancel + matched quiesce | Operation terminal; grant may remain usable for a distinct operation within its existing authorization. |
| Normal grant revoke/replacement + matched quiesce | Host `READY`; new preauthorized grant may activate, with fresh instance state. No old operation reopens. |
| Expiry, owner loss, reset or uncertain handoff | Host `FAULT_LATCHED`; authorized recovery/reconciliation leads to `INHIBITED`, then explicit operator rearm. Controller starts reset inhibited and rejects task frames until recovery. |

`RECONCILED` proves controller protocol/commanded-output facts, never cessation of measured wheel motion. Encoder/electrical measurements remain separately sourced evidence.

Completion uses the same unsent discard, immutable partial-frame recovery and quiesce barrier as cancellation. While awaiting that barrier, the group remains occupied and the next operation is ineligible. A later broader closure may supersede its transition/barrier; a narrower receipt cannot reconcile that broader closure. Recheck current deadlines and grant/fault state when processing its receipt; captured-earlier or late success cannot undo expiry, clear a fault or authorize another operation. Target reached followed by failed reconciliation is a valid combined outcome, not successful handoff.

## Operations, samples and observations

An operation binds immutable skill/configuration digest, permitted group, envelope and finite duration. The durable external request key maps to that one operation even after daemon restart. One operation occupies the group. Its stream ID is fresh and nonreusable; cancel atomically closes its stream without needing to revoke unrelated grant permissions.

Initial RPC proposal supplies an attempt-scoped stable request key and immutable parent digest, not an invented operation ID. The robot allocates and durably binds the operation ID before possible dispatch, then returns it. Authenticated query/cancel may use the stable key before that response; the [platform contract](platform-release-contract.md) owns key serialization, durable cancellation tombstones and non-admitting lookup. Allocated-key cancellation resolves to this kernel close path. Child submissions use the returned operation identity; the kernel sees only robot-issued identities under its runtime epoch, not a second durable key store.

V1 exposes latest-value samples, not arbitrary queued trajectories. Each sample has `(operation_id, stream_id, sequence)` plus its own digest, acquisition context and absolute deadline. A higher sequence replaces only the unsent mailbox; it cannot replace a started frame or controller effect. The current identical duplicate returns existing status and never refreshes deadlines; changed-payload duplicate is rejected. Older sequences outside the retained bounded result slot are rejected as retired, never replayed. Sequence exhaustion terminates the stream; wrap is forbidden. V1 rejects chunk/trajectory submission. A future chunk protocol must separately identify predicted, replaceable, dispatched and applied prefixes before supporting RTC-style policies.

The kernel and controller reject samples for closed operations, retired sessions, incompatible revisions or expired windows, even if their enclosing grant once matched. Durable unfinished operations become `OUTCOME_UNKNOWN` after restart; no automatic resend/new-key substitution is permitted.

Observation IDs are scoped to source boot/session and nonreusing sequence. The copied kernel context includes earliest/latest acquisition time, validity, source, clock-map and calibration revisions. Dispatch uses the oldest possible acquisition time for maximum-age checks; future/inconsistent intervals, absent retained IDs and excessive uncertainty reject. Fresh host receipt cannot replace acquisition time. Payload identity and inference lineage remain userspace obligations; this kernel record does not prove what a model saw.

V1 calibration, clock-map and fixed-limit revisions change **only while inhibited**. Updating them under the authority mutex invalidates dependent observations and queued samples, advances context revision and requires explicit rearm. No active hot calibration exists. For V1 slew limits, track the last complete controller-accepted sample and controller application time from its receipt; while its status is unknown, do not start another sample. Clamp elapsed-time credit to a profile maximum so silence does not permit an arbitrarily large step. The controller independently enforces the same configured numeric/slew ceiling against its actual last applied output. Protective disable may bypass ordinary slew limits under its fixed protective rule; its physical response requires qualification.

There is no assumed generic serdev callback-quiescence API. A target lacking a proven path needs a minimal reviewed kernel patch or is unsupported. Old FDs remain queryable as detached and never bind to a replacement endpoint; final reference release frees state. No teardown waits for an unreachable controller receipt. Forced unload is unsupported.

Keep serdev open with its runtime-PM usage reference while the endpoint is bound; do not permit autosuspend of the active transport. Verify the actual parent/UART driver honors that reference. Suspend preparation first inhibits/reconciles; suspend while active is refused. Unavoidable shutdown/disconnect closes local authority without claiming delivery. Resume, PM errors or changed clocks require fresh inhibited reconciliation/rearm. The controller's own expiry oscillator and output-disable behavior must remain operative through Linux/host power loss.

Reconcile through verified provider outcomes, or a provider-enforced upper bound only where that guarantee is established. Otherwise keep that capacity quarantined, including a possible dispatch whose reply/commit was lost. Operator acknowledgment alone cannot clear an unresolved debit. Ambiguous/corrupt reservation storage blocks new dispatch. Completed results retain only their output-storage reservation until consumed/expired and deleted; unused provider budget is returned only after verified settlement. Settled consumption remains charged to the policy accounting period, rather than making successful calls free. This conservative finite accounting may reduce availability but prevents restart/cancel loops bypassing the admission budget.

Profile acceptance records allowed control cases and violations, immediate fork/exec, unrelated errors of the same syscall, enforcement-install failure and reader loss. Custom BPF-LSM policy, ActPlane and Actime are optional later profiles; their installed version/path must earn a separate denial coverage claim. No argv-based kill is labelled pre-effect denial.

Loss of required enforcement closes launches, quarantines affected broker channels and terminates affected attempts; it cannot undo prior effects. Diagnostic-reader loss preserves enforcement, marks evidence incomplete and closes new diagnostic-profile launches. Existing server attempts may finish under installed isolation with incomplete reports; robot delegation follows its finite grant/evidence policy. Trace loss counters and unavailable hooks remain visible.

## 3. Durable intent, recorder health and replay

Before first possible dispatch, persist operation ID, client request key/digest, instance/grant/context and immutable configuration in the local intent database. Dispatch only after a successful durable commit and fresh live checks. Storage failure rejects new operations. After recovery, unfinished intents are `OUTCOME_UNKNOWN`; neither database restoration nor a retry silently resends them.

For each producer, retain three distinct frontiers:

- `read`: copied from the producer into bounded recorder memory.
- `queued`: accepted into a bounded persistence batch; still volatile.
- `durable`: required files flushed/synced and their checkpoint committed to the database.

The writer orders recording-file persistence before committing the checkpoint; recovery excludes unsupported checkpoints/tails from authoritative results, preserves raw remnants for diagnosis and reports the gap. Storage durability means the selected stack honored its tested flush contract, not survival of arbitrary media failure. The recorder authenticates source channels and assigns origin labels; agent payloads cannot claim kernel/controller origin. A hash proves content identity, not trustworthy authorship.

The robot profile must supply maximum volatile bytes/records, maximum age since durable progress, heartbeat interval and maximum permitted continuation after health loss. These are required finite inputs, not inferred from queue capacity. A trusted writer reports its durable frontier separately from reader acknowledgement. Reader alive with writer stalled therefore exhausts the age/budget. Repeated heartbeats with an unchanged frontier do not establish progress while required records are pending.

Crossing either bound closes new experimental admission **and revokes existing experimental streams** through the normal urgent path. No arbitrary continuation is authorized by a healthy read cursor. Kernel/controller protection never waits for fsync; reserve transition-event capacity and still expose overflow. Continuous sample dispatch is asynchronous inside an already durable operation; it has no per-sample fsync. A crash can lose its tail, including the final loss marker. Unfinished intents, producer/session changes and last durable frontiers expose that uncertainty; successful control does not imply a complete episode.

Each attempt has a capture manifest: profile/configuration digests; producer identities and clock domains/error bounds; requested and actually retained streams; payload-versus-metadata policy; sequence ranges/gaps; durable frontiers; interventions; retention/redaction; and replay eligibility with missing reasons. Server and robot retain their own authoritative portions; export links them without converting remote claims into local facts.

Metadata-only is the default and supports inspection. V1 **execution replay** requires the instance activation boundary plus the complete retained input/model-output/configuration and execution/intervention prefix to the requested interval; a hash of missing content fails eligibility. This establishes the specified initial state and history, not deterministic physical reproduction. A partial mid-skill capture permits **event playback** with explicit gaps and unknown reconstructed state, not execution replay from invented state. Replay-only checkpoints are deferred. Fresh inference reproduction is a separate experiment. Replay runs under a no-device/no-live-credential profile with no command-service route. MCAP, OpenTelemetry and Rerun remain format/export/viewer integrations; none owns completeness or durability policy.

## 4. Enrollment, scopes and recovery

Enrollment is local-only while inhibited. On the robot's protected administrative Unix socket, `actryn device enroll request` creates a device key and outputs a CSR plus fingerprint. An operator checks that fingerprint on the physical/local console, signs it with the site's offline issuer workflow, then uses `actryn device enroll install` locally to install the certificate and selected site trust root. There is no unauthenticated network enrollment endpoint. `actryn device pair` verifies that enrolled device fingerprint and site chain before recording the connection.

Use an established X.509/mTLS implementation. Separate certificate scopes for deployment, attempt proposal, observation/readout and operator grant/rearm; the site's issuance policy prevents deployment identities requesting operator scopes. Local policy maps authenticated principals to ceilings; a valid certificate is not a grant. Proposed credential defaults: device certificate 30 days, operator session 8 hours, workload/deployment certificate 5 minutes. These are administrative design defaults, not physical response bounds. Workload certificates require renewal through the authorized issuer; offline expiry never extends automatically.

On connection, validate certificate time and local revocation state; derive a remaining session deadline on the robot clock. Session/grant lifetime cannot exceed credential/delegation validity. Credential renewal authenticates future requests; it neither extends an issued grant nor revives an expired one. Clock uncertainty or rollback closes new authorization and inhibits affected task authority. Local revocation immediately closes that principal's sessions and revokes its grants. A disconnected robot cannot instantly learn a remote revocation; short-lived delegation bounds this exposure. Site policy may shorten it.

Rotate keys through authenticated issuer approval plus local installation of new trust material while inhibited. Reconnect, rotation and re-enrollment never rearm. Lost/compromised administrator credentials require physical/local privileged recovery: inhibit, reconcile, retire all grants/sessions, replace trust roots/keys as appropriate and explicitly rearm under the new identity. Lost robot keys require re-enrollment, never identity copying from a process checkpoint. Decommissioning revokes credentials and removes local secrets only after required evidence export/retention.

## 5. Immutable releases and useful demonstrations

Use one initial `volnlabs/actryn` monorepo, with userspace, portable core, kernel, firmware and target boundaries. Independently version/promote server, robot and target artifacts. A signed immutable promotion manifest pins component/image/package digests; RPC/UAPI/features and gateway/manager transport/service configuration; exact kernel build/config/module; wire vectors and firmware; target hardware, policy/calibration; dependency/weight licenses and notices; build provenance; and exact conformance/qualification evidence. Missing or incompatible required entries fail preflight. CI consumes immutable artifacts built from pinned revisions, never an assumption that one shared commit makes every component compatible.

The same release system has independent eligibility: implement and accept the server alongside hardware/kernel work, using its own profile inputs. A server manifest can promote after its isolation/report/cleanup checks without robot D0/D1/D4 qualification. Target publication records supported exact tuples; it neither upgrades an installed robot nor qualifies another combination. A robot manifest pins a compatible server RPC range but keeps its exact qualified local tuple. A server update cannot silently update kernel, firmware or robot policy. Regression checks reconstruct manifests, reject deliberate mismatches, and exercise supported client upgrades/downgrades against a fixed robot tuple.

Trusted-stack updates require inhibition, downstream reconciliation and recovery access before staging. Gateway replacement first closes associated contexts/grants; service restart cannot silently restore them. The launcher and privileged observer remain trusted server components, even though their release is independent of robot qualification. Activate only the complete compatible tuple; power interruption leaves an inhibited recoverable installation. Firmware recovery follows the actual target mechanism. Reverting software creates fresh epochs/instances and reconciles; it cannot restore grants or reverse motion. Preserve evidence before schema migration; unsupported downgrade is rejected, not attempted destructively.

Two proposed operator stories define scope. The guided CLI presents the same stages with principal, target/profile, limits, generations and stable request handles; grant/rearm/activation remain separately authorized explicit actions. An interrupted guide queries retained identities before proceeding and never resends an uncertain effect or automatically rearms:

1. **Server diagnosis:** install, `actryn doctor --role server`, `actryn attempt prepare <agent-digest> --profile server-restricted`, then `actryn attempt start <prepared-attempt>` without a robot grant. A multimodal batch exceeds its memory budget while a child attempts forbidden host-device access and an unauthorized broker method. `actryn attempt inspect` distinguishes resource facts, failed OS access, broker-attributed denial, missing evidence and model/tool context; `actryn evidence export <attempt-id>` retains the report; cleanup leaves no descendants/credentials. Repeat with an unrelated open failure to prevent false denial claims.
2. **Repeated robot experiment:** install/doctor/enroll/pair; prepare the server attempt before local skill instance/grant/activation; acquire an encoder-indexed restrained-wheel observation; let the agent propose one bounded index step through a fixed skill; independently judge displacement using retained encoder/instrument readings. Trusted `operation.finish` requests `SKILL_FINISHED` closure; only a timely matched quiesce receipt releases the group for a second normally completed step under the same live grant. Preserve task verdict separately from closure/reconciliation, including target reached followed by failed handoff. Normal cancel uses `CANCELLED`; the kernel contract defines first normal reason and dominating grant/fault/expiry precedence. Also cancel by request key before the first ID returns, then deliver the delayed proposal. Next exercise grant expiry: observe `FAULT_LATCHED`, perform authorized `actryn robot reconcile`, explicitly `actryn robot rearm`, issue/activate a fresh grant and run a new operation. Deliver the old response and show rejection. Rearm alone never authorizes that new operation. This is the engineering fixture; the buyer demonstration adds a selected robot's repeated visual alignment task with independently measured final position. Its endpoint/task acceptance must be chosen before claiming customer usefulness.

Stress both stories: fill broker capacity with delayed/oversized and uncancellable replies, cancel/terminate/restart, and verify finite retained debits, no late publication and service for another already-admitted attempt. Exhaust staging capacity and inject allocation/preparation failures while A executes; verify rejection preserves A and accounting settles. Separately kill the daemon and expect owner-loss/expiry. Race key cancellation against allocation/commit/submission, crash after tombstone commit before acknowledgment, and stall storage during allocated cancellation. Delay successful-completion receipts and race finish/cancel/expiry; no next operation becomes eligible early.

An operator other than the author repeats both on a fresh second installation of the same supported target/profile, measuring install, diagnosis and recovery effort. This repeatability gate precedes expansion to a second controller; a successful controller port is different evidence. The robot story requires independent displacement evidence; if encoder hardware is unavailable, qualify an alternative instrument and revised task criterion before substituting it. Controller acknowledgement alone cannot supply task success. Hosted provider/model identity remains unselected; recordings can support software fixtures but cannot stand in for a live task-success benchmark.

Adoption order is standard facility → supported public API → narrow adapter → extracted source/fork. Extraction requires a semantic gap, pinned unit/license, retained assumptions, regression tests and named patch owner. These contracts customize the surrounding machinery without importing whole frameworks or copying maintained APIs unnecessarily.

Validation still required: selected-runtime launch ordering and policy tests, gateway authentication/lifetime/resource fixtures, persistence/crash fixtures, credential recovery, release reconstruction, model suitability and all target/physical measurements. This document resolves design choices; it is not evidence that those checks passed.

## 5. Copper: local execution experiment behind our contract

**Decision: optional integration and benchmark candidate, not the authority core.** The inspected workspace is development code, not a selected supported release.

The [task API](https://github.com/copper-project/copper-rs/blob/b3c4c83d79d61d0357e50d431dd4c5c9ec4fece6/core/cu29_runtime/src/cutask.rs) offers explicit task lifecycle hooks; message and [monitor interfaces](https://github.com/copper-project/copper-rs/blob/b3c4c83d79d61d0357e50d431dd4c5c9ec4fece6/core/cu29_runtime/src/monitoring.rs) offer validity/error-handling context. ## Findings that change the design review

1. **A bounded numeric envelope is not a general motion verifier.** A:L200–204 keeps planning/perception outside the kernel and selects fixed predicates; A:L237 rejects malformed values and incompatible frames. Both are sensible, but “admitted” must explicitly mean the named fixed predicates passed. Counterexample: two individually legal arm poses can cause an inter-arm collision. GPT-Policy's own limitation section reports such collisions. Require each supported skill to name its trusted trajectory/collision/contact checks and unsupported scenes; keep their result distinct from kernel admission. Do not imply that adopting a constrained tool controller or a custom kernel resolves this problem.

2. **The chunk contract lacks a time-indexed commitment frontier.** A:L237 has a requested horizon and A:L249 distinguishes five horizons, but A:L282 describes continuous samples only through sequence/age rules. Counterexample: a delayed replacement chunk starts at index zero although its first samples correspond to time already executed; or a smoother conditions on an unclamped old chunk while the actual dispatcher clamped it. Add prediction horizon, execution horizon, control period, absolute local target-step/time alignment, and the actual accepted prefix to the local policy-adapter contract. Superseding chunks may replace only uncommitted work; stale elapsed samples cannot replay. Revocation invalidates the entire candidate stream. This belongs in userspace/local execution with bounded kernel admission, rather than a flow sampler in the kernel. RTC is an optional implementation for compatible policies, not a reason to defer defining these semantics.

3. **Research state and authority state need separate lineage.** A:L224–231 distinguishes artifact/instance/grant but does not specify evolving model context or learned option/progress state; A:L278 requires fresh activation state. Counterexample: a restarted planner carries old “grasp complete” memory into a newly rearmed attempt; an asynchronous Corrector response marks a replacement operation successful. Record model/checkpoint/provider identity, prompt/context compiler revision, demonstration references, observation references, inference request and operation/subtask identity, and local policy state reset rules. Attach inference/progress/diagnosis outputs to the exact operation epoch. A proposal should remain bounded even when the model hot-loads weights or changes hidden state. Do not silently support unrestricted live weight updates just because a research learner does them.

4. **An observation can be fresh but geometrically unsupported.** A:L243–247 handles acquisition age and estimates, but the kernel bridge's typed-state validity policy needs an explicit support/uncertainty contract. Counterexample: a tracker supplies a current timestamp for an object hidden throughout an entire video chunk, with compounded scale drift. Keep derivation/input lineage, visibility/support interval, frame/scale calibration and the estimate's validity conditions in userspace; expose only approved typed preconditions to the fixed gate. A current inference time cannot refresh stale measurement support. Deny contact-sensitive skills when their required support is unknown.

5. **“Failure attribution” must not become an authoritative causal claim.** A:L309 lets agents append explanations and A:L313 separates evidence dimensions. Preserve this distinction in the actual event schema. Counterexample: the object drops after a kernel clamp or stale rejection, but a learned grasp/planning discriminator assigns “planner failure” and contaminates its learning data. Record the proposed, admitted and delivered action plus intervention/rejection/gap history before assigning a model diagnosis. Store classifier distribution, model version, labels and unknown/ambiguous status separately from observed fault facts. A policy's progress discrepancy is useful for detection, not independently proven task success or causal responsibility.

6. **Evaluation must measure the task and timing regime actually supported.** A:L400–406 has good fault and commercial metrics, but lacks per-skill model-performance acceptance. Counterexample: rotated views of one scene are counted as independent trials; emitted actions per second are presented as closed-loop refresh rate; near-perfect simulator success is treated as contact reliability on the fixture. Add per-workflow task-success definitions, unique episode/scene counts, interventions, reset conditions, fixed comparison budgets, camera/geometry/latency shifts and paired latency traces. Keep generated-action throughput, fresh-observation inference frequency, actual dispatch rate and physical response separate. Research metrics are references, not inherited acceptance limits.

7. **The current selective-adoption table is not evidence that every research item was assessed.** Source-review §6 explicitly calls its dispositions design decisions. Its RTC/OxyGen row is too broad to establish model compatibility, and A:L385's deferred-input language does not expose the missing full papers or implementation releases. Retain deferral where appropriate, but attach this per-item matrix and make incomplete source depth visible. No paper reviewed here proves novelty of Voln's kernel authority architecture or customer demand for it.

## Ranked design findings

### 1. P1: The first endpoint remains an engineering candidate, not a selected supported target

Architecture locations: §4 “First enforceable transport” (line 188), §7 (lines 286–301), §11 delivery gates. Source availability alone is a weak selection criterion relative to native controller diagnostics, tooling, independent protective behavior, wiring and customer relevance. The document acknowledges the gap, but its concrete repository and backend layout can make the choice appear more settled than it is.

Counterexample: the local RP2040 program selects the runtime profile and FPGA image only with `fpga-runtime`; without it, both are `None` and execution stops. With it, `main.rs:78–124` explicitly describes candidate timing requiring hardware qualification. The standalone FPGA gate consumes `command_valid`; that module does not itself define host session expiry or a link watchdog. It cannot be cited alone as independent host-loss protection. [RP2040 source](../../ref/axiomos/firmware/shrike/rp2040/src/main.rs), [FPGA gate](../../ref/axiomos/firmware/shrike/fpga/shrike_safety_gate.sv).

Required decision: compare two concrete controller/fixture candidates against the same route-closure, host-loss, residual-work and recovery requirements before locking the backend. The custom kernel component remains mandatory. Gate: actual UART/pinmux/console exclusivity, buffer inventory, truncated-frame fault injection, endpoint restart/expiry, power-loss behavior, physical inhibit response and independent synchronized measurement. A preferred source tree does not substitute for any of these.

### 2. P1: Framework “stop”, timeout and automatic recovery are different effects

Architecture locations: §6 lifecycle, §7 controller fallback, §10 comparison references. A wrapper must preserve each native mechanism's meaning and prevent its recovery path from creating new effects after Voln revocation.

Counterexamples: [Spot leases](https://dev.bostondynamics.com/docs/concepts/lease_service.html) can become fresh when communication returns before another owner acquires; Voln expiry requires explicit recovery/rearm. Spot [Keepalive policies](https://dev.bostondynamics.com/docs/concepts/keepalive_service.html) are optional, removable, and may perform AutoReturn rather than stop. APYROBO's [watchdog source](https://github.com/apyrobo/Apyrobo/blob/173627442a48fa930ffe0e6fc21c2eabcc8db5ad/apyrobo/safety/watchdog.py#L178) can stop, open a gripper, or call a home function from a Python timer thread. Those latter actions can move equipment or release a payload. None should silently become the generic safe fallback.

Gate: declare brake/hold/torque-off/power-off/return-home separately, forbid automatic grant resurrection, and test each policy with the actual load and interrupted downstream work. Recovery commands traverse the same final authority boundary unless they belong to explicitly installed protective authority.

### 3. P1: Existing endpoint adapters often retain a raw writer or a competing lifecycle

Architecture locations: §3 final paragraph before §4 (line 153), §7 ROS routes (line 301), §10 reuse decisions. An upper-level client integration can be cheap; a qualified controller integration can require replacing the adapter's entire dispatch backend.

Counterexamples: Interlatent's [bus arbitration](https://github.com/Interlatent/Interlatent/blob/ab1e1f0dfc5cf81242c6187afed5f1dda5e4e960/packages/sdk/src/interlatent/behaviors/arbitration.py) checks PID/serial lockfiles, allows `force=True`, and continues unlocked if writing the cooperative lock fails. OM1's [Go2 connector](https://github.com/OpenMind/OM1/blob/3589af1214a6aa6b0058f30d4ae347ed31ebf265/plugins/actions/unitree/go2/autonomy/move.go#L409) publishes Twist directly over Zenoh. A ROS graph or kernel gate elsewhere does not govern those outputs.

Gate: enumerate every connector and alternate tool/service route, replace raw writers with typed Voln submissions, test that old messages cannot refresh an expired session, and label any retained privileged SDK worker as trusted. Do not promise the first Shrike kernel-enforcement claim for a network/vendor adapter.

### 4. P1: A second process watchdog does not survive whole-host failure

Architecture locations: §3 trust/topology, §4 host-freeze rule, §7 loss conditions. OpenRAL's separate “safety kernel” is a C++ userspace process; its independent deadman is independent of that process, not of Linux scheduling, power or the ROS dispatch graph.

Counterexample: the [deadman source](https://github.com/OpenRAL/openral/blob/8f0cfd054d61679b07509598d494f902e238aafb/packages/openral_safety_watchdog/openral_safety_watchdog/deadman_watchdog_node.py#L272) refreshes liveness on safe-action arrival with `time.time_ns()` and [publishes `/openral/estop`](https://github.com/OpenRAL/openral/blob/8f0cfd054d61679b07509598d494f902e238aafb/packages/openral_safety_watchdog/openral_safety_watchdog/deadman_watchdog_node.py#L365) from a ROS timer. Clock steps, delayed traffic and a stalled host therefore belong in any adaptation review. This selected source observation is not a claimed exploit or a complete OpenRAL safety assessment.

Gate: independently qualify endpoint host-loss behavior; distinguish application crash, host scheduling freeze, host power loss and controller failure. Use process monitors for detection/diagnosis while retaining controller-side bounded validity and the named protective mechanism.

### 5. P2: Adoption decisions need an ownership map, not “framework behind our contract” alone

Architecture locations: §5 containerd lifecycle, §6 authoritative mutation order, §10 Wendy/Copper references. Transitive capabilities may continue across agent restart; ros2_control owns hardware/controller lifecycles; Sugarcoat performs distributed fallback; dora and HORUS also own execution scheduling. These are real integration responsibilities, not interchangeable libraries.

Counterexample: [ros2_control's current controller-manager docs](https://control.ros.org/rolling/doc/ros2_control/controller_manager/doc/userdoc.html) describe auto-activation of hardware absent from the initial-state map, resource-dependent fallback activation and mode-switch jitter. A default spawner can activate hardware before a Voln rearm.

Gate: map native configure/activate/deactivate/restart/fallback transitions to Voln states and identify exactly one owner for each. Installation/reconfiguration must not arm; framework self-healing cannot mint a grant. Select one local scheduler if a measured need exists, rather than layering several.

### 6. P2: Runtime language and binary compatibility have already drifted

Architecture locations: §9 Python SDK, §10 agent-framework dispositions, previous source-review §6. A Python client does not imply a Python-based framework dependency remains maintainable.

Counterexamples: [OM1](https://github.com/OpenMind/OM1#pick-your-runtime) recommends its newer Go runtime and marks Python deprecated/unmaintained, with some capability parity unfinished. [HORUS](https://github.com/softmata/horus#get-started) warns its older PyPI bindings use an incompatible shared-memory format and requires matching CLI/cached source/bindings. [Libcanard](https://github.com/OpenCyphal/libcanard) describes significant v5 TX/RX/API evolution.

Gate: pin a released compatible binary tuple, reproduce a clean install/build and reconnect/restart tests on each target architecture, and assign one upgrade owner. Main-branch feature claims and historical language summaries must not determine release dependencies.

### 7. P2: Competitors already overlap the proposed governance product

Architecture locations: §1 buyer/workflow hypothesis, §10 novelty caveat. [ROSClaw](https://github.com/ros-claw/rosclaw#rosclawd-boundary) documents peer-bound permits, finite deadlines, resource leases, queue ownership, persisted consumption/receipts and disarmed restart. OpenRAL and AEROS expose overlapping admissibility boundaries. Their README claims are not qualified results, but they are enough to reject originality claims based solely on leases, receipts or an LLM-proposes/runtime-decides slogan.

Gate: compare one identical hostile-client/crash/revoke/recovery workload against a governed userspace baseline and the custom kernel implementation. Measure bypass resistance, failure coverage, integration effort and maintained code. Fixed kernel inclusion does not prove every additional feature needs custom implementation.

### 8. P2: Evaluation tools cannot approve an actuator profile

Architecture locations: §8 dataset export/replay, §11 comparative evidence. TDBench, VLMEvalKit and EmbodiedEvalKit assess perception/reasoning task behavior; Gymnasium and RAI Bench supply task interfaces; none measures endpoint expiry or physical stop by default.

Counterexample: VLMEvalKit [documents generation-based evaluation, prompt differences and optional LLM answer extraction](https://github.com/open-compass/VLMEvalKit). A higher score can reflect a changed extraction/prompt path without any improvement in robot command freshness or recovery. Gate: freeze dataset/model/prompt/judge versions, retain denied/clamped/intervened/unknown effects, and run physical conformance separately.

Wendy's inspected `NOTICE:90–96` records statically linked LGPL-2.1-or-later libusb in Linux/macOS CLI binaries. ## Recommended architecture consequences

1. Keep the custom kernel component and one typed dispatch owner. Keep the first physical target conditional until its complete controller/protective chain passes a comparative preflight.
2. Start with the native local loop and small SDK; evaluate a framework only for a demonstrated application/transport/deployment gap. Prefer its public API over extracting source when semantics fit.
3. Before any runtime integration, record an ownership table for launch, activation, watchdog refresh, fallback, persistence, update and command queues. Map each native failure/recovery behavior to Voln and identify raw-writer replacements.
4. Compare governed userspace systems rather than an intentionally weak CLI baseline. ROSClaw/OpenRAL/Spot are serious semantic references; none is physical qualification of Voln.
5. Keep model/task benchmarks and dataset conversion tooling in isolated offline environments. The product's endpoint conformance and physical evidence remain separate release gates.

It does not select supported versions for all projects, certify hardware, establish hard timing bounds, or complete dependency/legal audits. ## Findings that change the implementation plan

### S1 — High: select enforcement and denial evidence together

Architecture L167–174 and L208–216 correctly require installed coverage, but do not yet select enough of it to implement the server acceptance test. A successful policy compile, attached tracing program, killed process and pre-effect denial are different outcomes.

At inspected Actime revision `9c03598117af522c70e33695ca83dd4b38c12ff8`, `engine_supported_features` uses the conservative ActPlane 0.1.8 budget even when supplied a version string. Its enforcement preflight rejects rules needing unsupported file sinks/path matchers. ActPlane's broader engine capabilities cannot be assigned to this integration path. Its support matrix also distinguishes BPF-LSM blocking from tracepoint-triggered killing; argv-specific exec policies fall into the latter category. [Actime implementation](https://github.com/eunomia-bpf/actime/blob/9c03598117af522c70e33695ca83dd4b38c12ff8/crates/actime-core/src/enforceability.rs), [Actime policy documentation](https://github.com/eunomia-bpf/actime/blob/9c03598117af522c70e33695ca83dd4b38c12ff8/docs/policies.md), [ActPlane support matrix](https://github.com/eunomia-bpf/ActPlane/blob/404542899a2153af0952cbf0dc52aeab0b7c5034/docs/support-matrix.md).

**Correction:** start with a small executable coverage table: protected object/action, stock or custom enforcement point, install verification, process attribution, denial evidence source, unsupported routes, loss response. Choose concrete device-open, management-socket, network and syscall cases. Fail launch when a required denial cannot be installed. Do not describe an ordinary failed syscall as a policy-attributed denial without an attributable enforcement fact.

**Proof:** execute the known violation and an unrelated failure of the same syscall; disconnect the telemetry reader; fail enforcement installation; start descendants immediately. Check the claimed distinction in exported evidence. This is a software acceptance gate, not a reason to wait for robot hardware.

### S2 — High: specify the artifact execution path before designing a general behavior package

Architecture L224–229 names artifact/instance/proposal, but leaves the supported artifact's executable meaning unresolved. The practical first choice should be explicit: an untrusted agent image runs in a server sandbox and requests fixed, reviewed robot-local skills; only bounded targets cross to the robot. If generated robot-local code is required in V1, add a selected local launcher, sandbox, state owner and crash/replacement path now. Merely installing an immutable artifact does not select either model.

This agrees with architecture-attack finding 7. Keep a custom kernel component as required, but avoid accidentally inventing a robot plugin runtime while claiming to reuse the existing local controller. Model frameworks and Wasm do not resolve the choice by themselves.

**Proof:** trace one artifact digest through its real process, attempt identity, robot instance, grant and operation; replace/crash that process and demonstrate fresh state plus no inherited authority. A forged identity in a tool request must not change the launcher-assigned identity.

### S3 — Medium: provenance must state what is trusted and what is merely declared

Architecture L235 explicitly bounds a compromised server rather than trusting its model intent. Consequently, checking a recent observation ID cannot establish that a model proposal was derived from that observation. An agent can pair an old result with a newly available ID while its grant is still valid. This does not defeat the fixed local envelope; it defeats any stronger interpretation of “the model acted on this fresh image.”

**Correction:** have the trusted inference/tool bridge originate a request-context record binding request ID, attempt, observation IDs/digests, configuration and completion. Bind returned proposals to that context where the configured execution class permits it, and still recheck local state at admission/dispatch. Label agent-declared provenance separately. If the bridge shares the compromised server trust domain, this remains server-attested lineage, not robot-verifiable reasoning or proof of model attention. Do not add remote attestation unless the product actually requires that stronger claim.

**Proof:** replay an old response with a fresh observation ID, change calibration during inference and return a result after context closure. Test both normal trusted-bridge handling and deliberately untrusted metadata; report the different assurance levels. These tests establish association under an honest bridge; a compromised bridge can fabricate both records, so they cannot prove the model received or used the observations.

### S4 — Medium: enrollment and credential recovery need an actual protocol

Architecture L233–235 separates pairing/deployment/motion rights, but TLS plus finite delegation does not specify first enrollment, issuer trust or recovery after losing an administrator key. Installing a device-management tool is not permission to inherit its entire trust model.

**Correction:** choose one local enrollment flow with an operator-confirmed device fingerprint or equivalent physical/local bootstrap, explicit issuer and stored trust roots. Define scoped certificate renewal, local revocation, offline delegation expiry, lost-key recovery and decommissioning. Bind grants to the authenticated principal and current robot policy; reconnect or re-enroll must not rearm. Keep deployment credentials outside the motion administrator role.

**Proof:** wrong device during pairing; copied deployment credential attempting a grant; rotated/revoked identity offline; expired delegation on reconnect; replacement of trusted configuration while inhibited. These are design/negative-test requirements, not a claim that the current proposal leaks keys.

### S5 — Medium: evidence capture policy and replay eligibility must agree

Architecture L214 defaults to metadata, while L307–321 promises useful recorded-input/model-output replay. Those can coexist only if every attempt declares what was actually captured. A hash of a missing image cannot replay its content; an OTel trace cannot replace an omitted controller receipt. A viewer's available timeline is also not the authoritative retention record.

**Correction:** define an attempt capture manifest with required streams, source identities/clock domains, capture/retention policy, ranges and gaps, and an explicit replay eligibility result. Keep kernel-origin, controller-origin, manager-origin and agent-origin events distinguishable after export. Use read, queued-for-persistence and durable watermarks separately; architecture-attack finding 9 specifies the liveness failure case. Expensive image export and viewer work cannot share dispatch resources without measured bounds. Recorded-output playback differs from rerunning inference: complete capture neither guarantees reproducible model outputs nor authenticates records from a compromised server.

**Proof:** disable image capture, lose a model response, fill the recorder, stop its writer while the reader remains alive, crash before a durability checkpoint, and export a partially retained attempt. The UI must say what cannot be reconstructed and must never turn replay into a live proposal. [MCAP specification](https://mcap.dev/spec), [Rerun sinks](https://rerun.io/docs/concepts/logging-and-ingestion/sinks), [OTel trace API](https://opentelemetry.io/docs/specs/otel/trace/api/).

### S6 — Medium: adapting a project is not synonymous with copying its internals

The architecture's “extract useful probe patterns” direction is too broad as an adoption rule. AgentSight exposes a capture library; libbpf, MCAP and normal container runtimes already offer bounded APIs. Copying selected implementation files can increase our maintenance burden and lose upstream corrections. Conversely, Huatuo's full privileged deployment is much broader than a few per-attempt signals. [AgentSight README](https://github.com/eunomia-bpf/agentsight/blob/85bdb152653999bb5bf24a5b13c863bf8c949581/README.md), [Huatuo README](https://github.com/ccfos/huatuo/blob/fc7dac3247079707caaa33696462e3f287ac6cdd/README.md).

**Correction:** compare standard mechanism → supported narrow API → adapter → extracted source → maintained fork, in that order. Customize configuration, trust placement and our contracts before changing upstream code. Any source extraction must identify the exact unit, retained assumptions, changed semantics, tests, license provenance and patch owner. This honors the user's requirement to select and tailor every adopted component without making a fork a product requirement.

**Proof:** a dependency decision record must show the concrete user problem, rejected simpler option and maintenance/qualification cost. No full framework enters V1 merely because its README overlaps our vocabulary.
