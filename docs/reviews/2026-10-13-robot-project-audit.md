# Independent robot-project audit

Historical review of the preserved pre-patch baseline. See the [remediation record](2026-10-13-review-remediation.md) for the current design changes and remaining validation gates.

Date: 2026-10-13. Scope: ecosystem interface and maintenance review against [the proposed architecture](baseline/2026-10-13-volnlabs-system-architecture.md) and [the earlier source review](2026-10-13-source-review-baseline.md). A custom Linux kernel component in the first release is a fixed user requirement. It does not establish that the particular Shrike/UART backend, kernel-owned controller parser, or three-repository split is the best implementation.

**Verdict:** retain one authoritative dispatch owner, but do not approve the selected physical endpoint yet. None of the reviewed frameworks makes a universal kernel-enforced robot adapter possible merely by connecting its topic, SDK, or skill API. Existing projects already implement substantial governed-action, recovery and evidence semantics. Compare those semantics directly before claiming product differentiation or reimplementing their management features.

## Ranked design findings

### 1. P1: The first endpoint remains an engineering candidate, not a selected supported target

Architecture locations: §4 “First enforceable transport” (line 188), §7 (lines 286–301), §11 delivery gates. Source availability alone is a weak selection criterion relative to native controller diagnostics, tooling, independent protective behavior, wiring and customer relevance. The document acknowledges the gap, but its concrete repository and backend layout can make the choice appear more settled than it is.

Counterexample: the local RP2040 program selects the runtime profile and FPGA image only with `fpga-runtime`; without it, both are `None` and execution stops. With it, `main.rs:78–124` explicitly describes candidate timing requiring hardware qualification. The standalone FPGA gate consumes `command_valid`; that module does not itself define host session expiry or a link watchdog. It cannot be cited alone as independent host-loss protection. [RP2040 source](../../ref/axiomos/firmware/shrike/rp2040/src/main.rs), [FPGA gate](../../ref/axiomos/firmware/shrike/fpga/shrike_safety_gate.sv).

Required decision: compare two concrete controller/fixture candidates against the same route-closure, host-loss, residual-work and recovery requirements before locking the backend. The custom kernel component remains mandatory. Gate: actual UART/pinmux/console exclusivity, buffer inventory, truncated-frame fault injection, endpoint restart/expiry, power-loss behavior, physical inhibit response and independent synchronized measurement. A preferred source tree does not substitute for any of these.

### 2. P1: Framework “stop”, timeout and automatic recovery are different effects

Architecture locations: §6 lifecycle, §7 controller fallback, §10 comparison references. A wrapper must preserve each native mechanism's meaning and prevent its recovery path from creating new effects after Voln revocation.

Counterexamples: [Spot leases](https://dev.bostondynamics.com/docs/concepts/lease_service.html) can become fresh when communication returns before another owner acquires; Voln expiry requires explicit recovery/rearm. Spot [Keepalive policies](https://dev.bostondynamics.com/docs/concepts/keepalive_service.html) are optional, removable, and may perform AutoReturn rather than stop. APYROBO's [watchdog source](https://github.com/apyrobo/Apyrobo/blob/173627442a48fa930ffe0e6fc21c2eabcc8db5ad/apyrobo/safety/watchdog.py#L178) can stop, open a gripper, or call a home function from a Python timer thread. Those latter actions can move equipment or release a payload. None should silently become the generic safe fallback.

Gate: declare brake/hold/torque-off/power-off/return-home separately, forbid automatic grant resurrection, and test each policy with the actual load and interrupted downstream work. Recovery commands traverse the same final authority boundary unless they belong to explicitly installed protective authority.

### 3. P1: Existing endpoint adapters often retain a raw writer or a competing lifecycle

Architecture locations: §3 final paragraph before §4 (line 153), §7 ROS routes (line 301), §10 reuse decisions. An upper-level client integration can be cheap; a qualified controller integration can require replacing the adapter's entire dispatch backend.

Counterexamples: Interlatent's [bus arbitration](https://github.com/Interlatent/Interlatent/blob/ab1e1f0dfc5cf81242c6187afed5f1dda5e4e960/packages/sdk/src/interlatent/behaviors/arbitration.py) checks PID/serial lockfiles, allows `force=True`, and continues unlocked if writing the cooperative lock fails. OM1's [Go2 connector](https://github.com/OpenMind/OM1/blob/3589af1214a6aa6b0058f30d4ae347ed31ebf265/plugins/actions/unitree/go2/autonomy/move.go#L409) publishes Twist directly over Zenoh. A ROS graph or kernel gate elsewhere does not govern those outputs.

Gate: enumerate every connector and alternate tool/service route, replace raw writers with typed Voln submissions, test that old messages cannot refresh an expired session, and label any retained privileged SDK worker as trusted. Do not promise the first Shrike kernel-enforcement claim for a network/vendor adapter.

### 4. P1: A second process watchdog does not survive whole-host failure

Architecture locations: §3 trust/topology, §4 host-freeze rule, §7 loss conditions. OpenRAL's separate “safety kernel” is a C++ userspace process; its independent deadman is independent of that process, not of Linux scheduling, power or the ROS dispatch graph.

Counterexample: the [deadman source](https://github.com/OpenRAL/openral/blob/8f0cfd054d61679b07509598d494f902e238aafb/packages/openral_safety_watchdog/openral_safety_watchdog/deadman_watchdog_node.py#L272) refreshes liveness on safe-action arrival with `time.time_ns()` and [publishes `/openral/estop`](https://github.com/OpenRAL/openral/blob/8f0cfd054d61679b07509598d494f902e238aafb/packages/openral_safety_watchdog/openral_safety_watchdog/deadman_watchdog_node.py#L365) from a ROS timer. Clock steps, delayed traffic and a stalled host therefore belong in any adaptation review. This selected source observation is not a claimed exploit or a complete OpenRAL safety assessment.

Gate: independently qualify endpoint host-loss behavior; distinguish application crash, host scheduling freeze, host power loss and controller failure. Use process monitors for detection/diagnosis while retaining controller-side bounded validity and the named protective mechanism.

### 5. P2: Adoption decisions need an ownership map, not “framework behind our contract” alone

Architecture locations: §5 containerd lifecycle, §6 authoritative mutation order, §10 Wendy/Copper references. Transitive capabilities may continue across agent restart; ros2_control owns hardware/controller lifecycles; Sugarcoat performs distributed fallback; dora and HORUS also own execution scheduling. These are real integration responsibilities, not interchangeable libraries.

Counterexample: [ros2_control's current controller-manager docs](https://control.ros.org/rolling/doc/ros2_control/controller_manager/doc/userdoc.html) describe auto-activation of hardware absent from the initial-state map, resource-dependent fallback activation and mode-switch jitter. A default spawner can activate hardware before a Voln rearm.

Gate: map native configure/activate/deactivate/restart/fallback transitions to Voln states and identify exactly one owner for each. Installation/reconfiguration must not arm; framework self-healing cannot mint a grant. Select one local scheduler if a measured need exists, rather than layering several.

### 6. P2: Runtime language and binary compatibility have already drifted

Architecture locations: §9 Python SDK, §10 agent-framework dispositions, previous source-review §6. A Python client does not imply a Python-based framework dependency remains maintainable.

Counterexamples: [OM1](https://github.com/OpenMind/OM1#pick-your-runtime) recommends its newer Go runtime and marks Python deprecated/unmaintained, with some capability parity unfinished. [HORUS](https://github.com/softmata/horus#get-started) warns its older PyPI bindings use an incompatible shared-memory format and requires matching CLI/cached source/bindings. [Libcanard](https://github.com/OpenCyphal/libcanard) describes significant v5 TX/RX/API evolution.

Gate: pin a released compatible binary tuple, reproduce a clean install/build and reconnect/restart tests on each target architecture, and assign one upgrade owner. Main-branch feature claims and historical language summaries must not determine release dependencies.

### 7. P2: Competitors already overlap the proposed governance product

Architecture locations: §1 buyer/workflow hypothesis, §10 novelty caveat. [ROSClaw](https://github.com/ros-claw/rosclaw#rosclawd-boundary) documents peer-bound permits, finite deadlines, resource leases, queue ownership, persisted consumption/receipts and disarmed restart. OpenRAL and AEROS expose overlapping admissibility boundaries. Their README claims are not qualified results, but they are enough to reject originality claims based solely on leases, receipts or an LLM-proposes/runtime-decides slogan.

Gate: compare one identical hostile-client/crash/revoke/recovery workload against a governed userspace baseline and the custom kernel implementation. Measure bypass resistance, failure coverage, integration effort and maintained code. Fixed kernel inclusion does not prove every additional feature needs custom implementation.

### 8. P2: Evaluation tools cannot approve an actuator profile

Architecture locations: §8 dataset export/replay, §11 comparative evidence. TDBench, VLMEvalKit and EmbodiedEvalKit assess perception/reasoning task behavior; Gymnasium and RAI Bench supply task interfaces; none measures endpoint expiry or physical stop by default.

Counterexample: VLMEvalKit [documents generation-based evaluation, prompt differences and optional LLM answer extraction](https://github.com/open-compass/VLMEvalKit). A higher score can reflect a changed extraction/prompt path without any improvement in robot command freshness or recovery. Gate: freeze dataset/model/prompt/judge versions, retain denied/clamped/intervened/unknown effects, and run physical conformance separately.

Defer is not a judgment that a project is poor.

## License scope actually checked

This is a concrete redistribution obligation to review, even though the top-level project is described as Apache-2.0 in the earlier source review. AEROS's inspected repository LICENSE is AGPL-3.0 text and `src/aeros/interfaces.py` has an Apache-2.0 SPDX header. Its README lists additional separately licensed integration directories. This establishes file-level scope for the checked interface, not automatic permissive licensing for arbitrary copied core code or all transitive dependencies. Do not infer that a project integration always has a particular legal consequence without the exact selected files/distribution being reviewed.

The checked local Shrike FPGA module carries `MIT OR Apache-2.0`; local vendor firmware/hardware has separate `LICENSE.md` and `LICENSE_HW.md` files. Other project rows use license clearance as a gate; README badges or repository language labels were not treated as completed license inspections.

## Recommended architecture consequences

1. Keep the custom kernel component and one typed dispatch owner. Keep the first physical target conditional until its complete controller/protective chain passes a comparative preflight.
2. Start with the native local loop and small SDK; evaluate a framework only for a demonstrated application/transport/deployment gap. Prefer its public API over extracting source when semantics fit.
3. Before any runtime integration, record an ownership table for launch, activation, watchdog refresh, fallback, persistence, update and command queues. Map each native failure/recovery behavior to Voln and identify raw-writer replacements.
4. Compare governed userspace systems rather than an intentionally weak CLI baseline. ROSClaw/OpenRAL/Spot are serious semantic references; none is physical qualification of Voln.
5. Keep model/task benchmarks and dataset conversion tooling in isolated offline environments. The product's endpoint conformance and physical evidence remain separate release gates.

This report checks project identities and selected primary interfaces, with targeted source counterexamples. It does not select supported versions for all projects, certify hardware, establish hard timing bounds, or complete dependency/legal audits. Those limitations are explicit rather than hidden behind a long candidate list.
