# Actryn v0.0.1 implementation plan

Approved in conversation on 2026-10-16. The persistent goal is delivery of the
external developer preview described here, not documentation completion.

## Goal

One isolated OCI agent, one fixed wheel-index skill and a real Linux authority
driver/serdev backend form a complete tested workflow. External developers get
an offline deterministic demonstration and a separately tested live hosted-model
path. Physical activation is unavailable. Completion means a verified release
candidate ready for publication; remote push/merge/publication is separate.

## Binding sources and defaults

- [Architecture](../specs/architecture.md), [kernel contract](../../architecture/kernel-controller-contract.md),
  and [platform contract](../../architecture/platform-release-contract.md) retain their
  authority, cancellation, persistence, resource and evidence semantics.
- The preview scopes D0/D1 to a non-actuating software target; D2/D3 and a fresh
  installation by another developer are required. Physical D4/D5 remain unmet.
- Debian 13 x86-64 development/server host; Debian 13 ARM64 QEMU robot guest,
  PL011 UART with exclusive serdev binding, controller fixture outside the guest.
- Rust services/CLI/reference reducer, Python SDK, C loadable authority module.
  C is the selected 6.12 implementation; no Rust kernel API backport is required.
- systemd/containerd, maintained TLS/Protobuf RPC, SQLite intents and MCAP recordings.
- OpenAI Responses `gpt-5.4-mini-2026-03-17`, pinned prompt/schema, broker-held
  credentials, finite reservations, no automatic retries or provider-hosted tools.
- One active agent and one active wheel-group operation in the demonstration;
  bounded staged/retiring capacity remains accounted. Tests may use smaller limits
  and multiple isolated attempts to verify per-attempt/global accounting.
- No live device passthrough, physical target manifests or automatic grant/rearm.
- No new OS, custom JIT/scheduler, generated robot-local code, plugins, trajectories,
  additional controllers, local inference, training or fleet UI.

## Milestones

### M0: baseline and release specification

Preserve original documents, freeze software-only scope, schemas and finite
budgets, record dependency/source provenance, select exact Debian kernel/build
and inspect exported serdev/lifetime/teardown interfaces. Missing build evidence
remains an open gate, never a mock implementation pass.

### M1: authority and fixture

Canonical versioned UAPI, kernel authority transitions and exclusive UART binding;
fixture wire v2, clock/session identities, absolute expiry, applied receipts and
quiescence; deterministic controller and independent fault/golden-vector tests.
Commands must traverse the actual kernel/serdev/emulated UART path.

### M2: independent server

Prepared attempt identity, policy installation and verification before start;
restricted broker and credentials; atomic preparation/delegated-work reservations;
durable unknown external debits; bounded diagnostics, cleanup and export without
a Robot dependency. Implement alongside M1 after shared contracts are frozen.

### M3: robot and developer workflow

Local enrollment/pairing, manager-verified mTLS and separate unprivileged relay;
fixed `wheel.index_step.v1`; durable request-key identity and cancellation before
ID reply; finish/cancel/reconcile/fault/rearm; CLI and Python SDK use the same API.

Install -> diagnose -> enroll/pair -> prepare attempt and skill -> explicit local
rearm/authorise/activate -> start agent -> observe/propose -> kernel dispatch ->
finish/cancel -> reconcile -> inspect/export. Normal completion may reuse a valid
grant for a new operation. Fault recovery requires explicit rearm and fresh grant.

### M4: release qualification

Installable artifacts, repeatable QEMU environment, offline assets, checksums,
signing metadata, pinned compatibility manifests, interrupted-update/recovery tests,
full deterministic suite, bounded live-model test and independent developer install.
Preserve evidence against exact source/configuration/binary hashes.

## Acceptance matrix

Each row starts NOT_RUN; the progress ledger points to actual test commands and
retained evidence. A passing model/unit test is not kernel or physical acceptance.

| ID | Required behavior |
|---|---|
| A01 | Two natural completions under one grant; next operation waits for reconciliation. |
| A02 | Cancel absent key / allocated key before ID reply; persistence/submission races and lost acknowledgements. |
| A03 | Expired/retired/replayed/changed-duplicate work cannot renew or regain authority. |
| A04 | Every process/guest/controller restart preserves unknown outcomes and prevents automatic resend. |
| A05 | Broker reservations survive cancellation, oversized replies, unknown external work and restart. |
| A06 | Malformed UAPI, task identity/FD transfer/owner exit, concurrent closure, detach/rebind and PM faults. |
| A07 | Every-byte-offset cancellation, short/zero/error writes, retained bytes and invalid/late receipts. |
| A08 | Preparation/queue/broker/recording exhaustion preserves reserved closure capacity and active-work semantics. |
| A09 | Storage stall cannot block urgent allocated closure; failed durability cannot authorize new effects. |
| A10 | Forged/replayed/flooded gateway traffic and retained FDs cannot widen authority; local recovery works offline. |
| A11 | Evidence origin, gaps and read/queued/durable frontiers remain distinct; complete-prefix execution replay only. |
| A12 | Clean install, mismatched tuple rejection and interrupted update/rollback without restored grants. |
| A13 | Pinned live hosted-model proposals traverse the real isolated and kernel-gated path. |
| A14 | Another developer installs, diagnoses, cancels/recovers and exports evidence using shipped instructions. |
| A15 | KUnit/selftests, independent contract tests and separately identified lockdep/KASAN/KCSAN runs. |
| A16 | Software latency/overhead/loss and competent userspace comparison; no predetermined superiority claim. |
